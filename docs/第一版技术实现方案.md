# 第一版技术实现方案

更新时间：2026-06-30

## 1. 方案目标

本方案用于指导 `AI-Agent` 第一版从静态原型进入工程化实现。

第一版不追求一次做完整系统，而是先跑通一条可以演示、可以验收、可以继续扩展的核心闭环：

```text
目标 -> 资料 -> AI 整理 -> 计划 -> 打卡 -> 进度
```

技术实现的重点是：

```text
1. 保留当前 app/ 静态原型作为 MVP-0 演示基础。
2. 明确 MVP-1 的前后端边界、数据库对象和第一批 API。
3. AI 能先 mock、后真实接入，避免被模型接口阻塞。
4. 登录、PDF 上传、正式部署默认放到 MVP-2。
```

### 1.1 评估结论

当前方案方向正确，适合作为第一版工程化路线图。

需要优化的地方主要有三点：

```text
1. MVP-1 范围仍然偏大，如果同时做目标、资料、AI、计划、打卡、进度、闪卡、测试题和问答，容易拖慢第一轮落地。
2. 数据对象设计比较完整，但第一轮建表需要分优先级，避免为了未来功能提前付出过多实现成本。
3. API 清单适合做最终边界，但开工时需要再拆成 MVP-1A / MVP-1B，否则任务颗粒度不够清楚。
```

优化原则：

```text
先做一条最短真实闭环，再补学习增强功能。
MVP-1A 只证明前端可以调用后端、数据库能保存、AI 层可替换。
MVP-1B 再补闪卡、测试题、问答和延期调整。
MVP-2 再做登录、PDF、部署和多用户。
```

## 2. 阶段拆分

### 2.1 MVP-0：静态 / 本地演示闭环

目标：

```text
用当前 app/ 原型讲清楚产品主流程，让导师和协作成员先确认方向。
```

保留内容：

```text
app/index.html
app/app.js
app/styles.css
localStorage 本地存储
mock AI 输出
单用户数据
```

必须能演示：

```text
1. 创建成长目标。
2. 添加一份文本资料或网页链接。
3. 生成资料摘要、知识点、闪卡和测试题。
4. 生成短期行动计划。
5. 完成今日任务打卡。
6. 查看简单进度。
```

不在 MVP-0 做：

```text
后端服务
数据库
真实登录
真实 AI 接口
PDF 上传
线上部署
```

### 2.2 MVP-1：工程化最小版

目标：

```text
在不扩大产品范围的前提下，把主流程接入最小后端、数据库和可替换 AI 层。
```

必须实现：

```text
1. 前端从 localStorage 逐步改为调用 API。
2. 后端提供目标、资料、计划、打卡、进度相关接口。
3. 数据库持久化核心对象。
4. AI 整理模块支持 mock 和真实模型两种模式切换。
5. 单用户模式跑通完整主线。
```

MVP-1 建议再拆成两小步：

```text
MVP-1A：最小工程闭环
创建目标 -> 添加资料 -> AI 摘要 -> 生成计划 -> 完成打卡 -> 查看进度

MVP-1B：学习增强闭环
闪卡 -> 测试题 -> 资料问答 -> 简单延期调整
```

MVP-1A 完成口径：

```text
1. 刷新页面后目标、资料、计划、打卡记录不丢失。
2. 关闭真实 AI 时，mock AI 能稳定完成演示。
3. 打开真实 AI 时，至少资料摘要接口可以真实调用。
4. 前端不再只依赖 localStorage 完成核心流程。
```

MVP-1 暂缓：

```text
注册登录
多用户隔离
PDF 上传与解析
复杂网页解析
正式生产部署
复杂测试平台
```

### 2.3 MVP-2：完整化增强

目标：

```text
补齐真实用户系统、文件能力、部署和更完整测试，让项目接近可公开试用。
```

候选内容：

```text
1. 注册、登录、退出和登录状态保持。
2. 用户数据隔离。
3. PDF 上传、文本提取和资料入库。
4. 更完整的错误处理和接口校验。
5. 云端部署。
6. 基础自动化测试。
```

## 3. 第一版技术栈

### 3.1 MVP-0 技术栈

```text
前端：HTML + CSS + 原生 JavaScript
存储：localStorage
AI：前端 mock 逻辑
运行方式：直接打开 app/index.html 或本地静态服务
```

选择理由：

```text
当前原型已存在，适合继续作为产品流程演示版本，不需要立即重构。
```

### 3.2 MVP-1 建议技术栈

```text
前端：继续复用 app/，先用原生 fetch 调用后端 API
后端：Node.js + Express
数据库：SQLite
数据库访问：先用轻量 db helper 和 SQL，不急着引入 ORM
AI 接入：独立 aiService，支持 mock / real 两种模式
环境变量：.env 保存模型配置和运行模式
接口格式：REST API + JSON
```

选择理由：

```text
1. Node.js 和前端 JavaScript 语言一致，学习成本低。
2. Express 足够支撑第一批 REST API，不引入过重框架。
3. SQLite 适合本地开发和演示，避免数据库部署成本。
4. aiService 独立封装，后续替换模型或继续 mock 都更容易。
```

### 3.3 MVP-2 可升级方向

```text
前端：根据需要再迁移到 Vue / React
数据库：从 SQLite 迁移到 PostgreSQL / MySQL
认证：JWT 或 session
文件处理：PDF 文本提取服务
部署：前端静态托管 + 后端云服务 + 云数据库
```

## 4. 是否保留当前 app/ 静态原型

结论：

```text
保留。
```

保留方式：

```text
1. MVP-0 继续把 app/ 作为可直接演示版本。
2. MVP-1 不立即推倒重写，而是在 app/app.js 中逐步抽出 API 调用层。
3. 如果后续迁移到 Vue / React，再把当前页面作为交互和字段参考。
```

```text

    services/
```

MVP-1 期间的前后端关系：

```text

```

## 6. 最小数据库对象

MVP-1 先使用单用户模式，可以在表中预留 `user_id` 字段，但不实现真实用户系统。

数据库设计约定：

```text
1. API 字段使用 camelCase，数据库字段使用 snake_case。
2. MVP-1 统一使用默认用户 ID：default_user。
3. JSON 字段先用 text 存储，读写时由后端统一 parse / stringify。
4. created_at / updated_at 统一使用 ISO 时间字符串。
5. 先用 schema.sql 建表，后续再补正式 migration 工具。
```

建表优先级：

```text
MVP-1A 必建：goals、materials、material_summaries、plan_tasks、checkin_records
MVP-1B 再建：flashcards、quiz_questions
MVP-2 再正式启用：users
```

## 8. AI 接口接入方式

### 8.1 设计原则

AI 能力不直接写进路由或前端页面，而是统一封装到 `aiService`。

路由层只负责接收请求、读取数据库、调用服务和返回 JSON。
AI 提示词、mock 数据和真实模型调用都放在服务层，避免前端和路由文件变复杂。

建议结构：

```text
server/src/services/aiService.js
server/src/services/mockAiService.js
server/src/services/realAiService.js
```

对外提供：

```text
summarizeMaterial(material, goal)
generatePlan(goal, materials, options)
generateFlashcards(material)
generateQuiz(material)
answerQuestion(question, context)
```

### 8.2 mock / real 切换

环境变量：

```text
AI_MODE=mock
AI_PROVIDER=openai
AI_API_KEY=
```

可选值：

```text
mock：返回固定模板或规则生成内容，用于本地开发和无 key 演示。
real：调用真实大模型接口。
```

MVP-1 最低要求：

```text
1. mock 模式必须稳定可用。
2. real 模式可以先只接通资料摘要接口。
3. 如果真实模型不可用，页面仍能回退到 mock 模式演示。
4. 后端日志要能看出当前使用的是 mock 还是 real。
```

### 8.3 AI 输出结构

资料整理输出：

```json
{
  "summary": "资料摘要",
  "keyPoints": ["知识点 1", "知识点 2"],
  "difficulties": ["难点 1", "难点 2"],
  "learningOrder": ["先理解概念", "再做练习"],
  "smallTasks": ["完成 10 分钟朗读", "整理 5 个例句"]
}
```

计划输出：

```json
{
  "tasks": [
    {
      "dayIndex": 1,
      "title": "学习资料核心概念",
      "description": "阅读摘要并整理 3 个关键点"
    }
  ]
}
```

闪卡输出：

```json
{
  "cards": [
    {
      "front": "什么是刻意练习？",
      "back": "围绕明确目标、即时反馈和持续修正进行的练习方式。"
    }
  ]
}
```

## 11. 测试方式

MVP-1 先做最小可验证测试，不追求完整测试体系。

MVP-1A 手动验收流程：

```text
1. 启动后端服务。
2. 打开前端页面。
3. 创建一个成长目标。
4. 添加一份资料。
5. 点击 AI 整理，确认摘要和知识点生成并保存。
6. 生成 7 天行动计划。
7. 完成今日任务打卡。
8. 查看进度是否变化。
9. 刷新页面，确认数据仍存在。
```

MVP-1A 通过标准：

```text
1. 后端无启动报错。
2. /api/health 返回 success。
3. 数据库文件中能看到目标、资料、摘要、任务和打卡记录。
4. 前端完整流程不需要手工改 localStorage。
5. AI_MODE=mock 时可以无外部依赖完成演示。
```


## 12. 部署方式

MVP-0：

```text
不要求正式部署，本地打开或本地静态服务即可。
```

MVP-1：

```text
默认本地演示，不强制上云。
如果必须给导师远程访问，可以临时使用内网穿透或轻量云服务。
```

MVP-2：

```text
前端：静态托管
后端：云服务器或云函数
数据库：云数据库或托管 PostgreSQL / MySQL
文件：对象存储
```

## 13. 开发顺序建议

```text
1. 确认本方案和 MVP-1A 边界。
2. 新建 server/ 后端工程。
3. 建 SQLite 数据库和 MVP-1A 核心表。
4. 实现 health API。
5. 实现 goals API：先做列表、创建、详情。
6. 实现 materials API：先做列表、创建。
7. 实现 aiService mock 模式和 summarize 接口。
8. 实现 plans、tasks 和 checkin。
9. 实现 goal progress 统计接口。
10. 前端 app/ 接入 MVP-1A API。
11. 跑通 MVP-1A 验收流程。
12. 再进入 MVP-1B：闪卡、测试题、问答、延期调整。
13. 最后再决定是否接真实 AI 和是否提前做登录。
```
