# MVP 第一版进度评估与下一步计划

更新时间：2026-07-01  
当前基准分支：`dev`  
评估对象：陈负责的目标/计划/打卡/进度模块，赵负责的资料/AI 整理/闪卡/测试题模块

## 1. 总体结论

目前你和赵的工作在后端数据层已经基本对齐：两个人负责的核心模块都已经从前端 `localStorage/mock` 逐步迁移到了 Python 后端、FastAPI 接口和 SQLite 持久化存储。

但从完整 MVP 第一版来看，现在还不是严格意义上的“学习智能体”，更准确地说是一个“可持久化的学习助手 MVP”。它已经具备目标管理、资料管理、计划生成、打卡记录、进度统计、资料整理、闪卡和测试题的基础能力，但真实 AI 能力、前端全量接口接入、跨模块联动、用户隔离和部署还需要继续补齐。

当前阶段判断：

| 维度 | 当前状态 | 结论 |
| --- | --- | --- |
| 后端 API | 目标模块和资料模块均已实现核心接口 | 基本完成 |
| SQLite 持久化 | 目标、任务、打卡、资料、摘要、闪卡、测试题均已接入 SQLite | 基本完成 |
| 自动化测试 | 已有目标模块测试和资料模块测试 | 基本完成 |
| 前端接后端 | 目标模块已接入后端，资料模块仍需继续确认和补齐 | 部分完成 |
| 真实 AI 能力 | 当前仍主要是 mock/rule-based 生成 | 未完成 |
| 学习智能体闭环 | 目标、资料、打卡、进度之间的智能联动还不够 | 未完成 |
| 部署与协作规范 | 已有分支/PR 流程，但还没有 CI 和部署 | 部分完成 |

## 2. 陈和赵的工作是否对齐

### 2.1 已经对齐的地方

| 对齐项 | 陈：目标模块 | 赵：资料模块 | 当前判断 |
| --- | --- | --- | --- |
| 技术栈 | Python + FastAPI + SQLite | Python + FastAPI + SQLite | 已对齐 |
| 数据持久化 | `backend/app/services/store.py` | `backend/app/services/material_store.py` | 已对齐 |
| API 风格 | `ok(data)` 统一响应格式 | `ok(data)` 统一响应格式 | 已对齐 |
| 错误处理 | 404、422 等 HTTP 异常 | 404、409、422 等 HTTP 异常 | 基本对齐 |
| 自动化测试 | `backend/tests/test_goal_flow.py` | `backend/tests/test_material_flow.py` | 已对齐 |
| Smoke 测试 | `backend/smoke_api.py` 覆盖目标和资料主流程 | 同一脚本覆盖 | 已对齐 |
| Git 协作 | 功能分支开发，PR 合入 `dev` | 功能分支开发，PR 合入 `dev` | 已对齐 |

### 2.2 仍然没有完全对齐的地方

| 未对齐项 | 当前表现 | 建议处理 |
| --- | --- | --- |
| 前端资料模块接后端 | `app/app.js` 中仍能看到大量资料、闪卡、测试题相关的本地状态和 `localStorage` 逻辑 | 赵优先检查资料模块是否已经完整调用 `/api/materials` 系列接口 |
| 前端数据来源 | 目标模块更偏向后端 API，资料模块仍可能混有本地生成和本地保存 | 统一成“核心数据来自后端，前端只负责展示和交互” |
| AI 能力 | 当前资料摘要、闪卡、测试题仍是 mock 或规则生成 | MVP 第一版可以先保留 mock，但文档中要明确“AI 可替换服务” |
| 跨模块联动 | 目标、资料、计划、打卡、进度之间还没有形成真正智能闭环 | 先补目标和资料的关联展示，再考虑 AI 计划调整 |
| 接口文档 | 目标模块已有接口对照文档，资料模块还需要同步更新实际实现 | 赵补齐资料模块前后端接口对照 |

结论：后端实现方向已经对齐，前端和产品闭环还需要继续对齐。

## 6. MVP 第一版验收标准

第一版可以按下面标准验收。

### 6.1 后端验收

1. `python -m pytest backend/tests -v` 全部通过。
2. `python backend/smoke_api.py` 可以跑通。
3. 后端重启后，目标、任务、打卡、资料、摘要、闪卡、测试题数据不丢失。
4. `/docs` 中能看到目标、任务、进度、资料相关接口。
5. 常见错误能返回合理状态码，例如 404、409、422。

### 6.2 前端验收

1. 可以在页面创建目标。
2. 可以生成目标计划。
3. 可以完成任务打卡。
4. 可以查看进度统计。
5. 可以新增资料并绑定目标。
6. 可以生成资料摘要、闪卡、测试题。
7. 刷新页面或重启后端后，核心数据仍能从后端读取。
8. 页面不需要手动修改 `localStorage` 才能完成主流程。

### 6.3 协作验收

1. `dev` 分支保持可运行。
2. 每个功能从独立分支开发。
3. PR 描述说明改了什么、如何测试、有什么风险。
4. 合并前没有冲突。
5. 合并后本地同步最新 `dev`。

## 7. 当前风险

| 风险 | 影响 | 建议 |
| --- | --- | --- |
| 前端仍残留较多 `localStorage` | 数据可能看起来保存了，但实际没有进入后端 | 逐个页面检查数据来源 |
| 资料模块 AI 仍是 mock | 项目还不能称为真正 AI Agent | MVP 第一版先标注 mock，第二阶段接真实 AI |
| SQLite 迁移机制较简单 | 表结构变更时容易出错 | 现阶段先少改表结构，后续学习 Alembic |
| 没有用户系统 | 多用户数据会混在一起 | MVP 第一版保持单用户假设 |
| 没有 CI | PR 合并前容易忘记跑测试 | 尽快加 GitHub Actions |
| 分支基于旧 `dev` 开发 | 容易出现大面积冲突 | 新功能前先 `git switch dev` + `git pull origin dev` |

## 8. 阶段评估

以“学习智能体 MVP 第一版”为目标，当前完成度可以这样判断：

| 模块 | 完成度 | 说明 |
| --- | --- | --- |
| 后端接口 | 80% | 核心接口已经有，仍需继续统一文档和错误处理 |
| 数据持久化 | 85% | 目标和资料模块均已 SQLite 化 |
| 自动化测试 | 75% | 核心流程有测试，跨模块和前端 E2E 还没有 |
| 前端接入 | 60% | 目标模块较完整，资料模块需继续确认和改造 |
| AI 能力 | 30% | 当前主要是 mock/rule-based，不是真实 AI |
| 产品闭环 | 60% | 可以演示学习助手流程，但智能联动还弱 |

综合判断：当前处在 MVP-1A 基本完成、MVP-1B 准备开始的状态。

下一步最重要的事情不是继续加很多新功能，而是把已有功能串成稳定闭环：前端真正走后端 API，数据重启不丢失，测试能稳定通过，文档能解释清楚。
