# 两人协作开发分工文档

更新时间：2026-06-30

## 1. 文档目的

本文件用于明确 `AI-Agent` 在陈、赵两人协作阶段的职责边界、协作流程、Git 使用方式和功能验收标准。

目标是避免口头沟通后遗忘、需求反复变化、代码互相覆盖、功能完成标准不清楚等问题。

## 2. 协作原则

两人是同门，方向一致，不建议长期切成“一个只管产品、一个只管技术”。

当前采用：

```text
共同定方向 + 功能闭环主责 + 交叉评审
```

日常开发主规则：

```text
以后日常模块分工优先按 docs/daily/2026-06-30工作安排.md 推进。
陈主线：目标管理 -> 行动计划 -> 今日任务 -> 打卡 -> 进度统计。
赵主线：资料管理 -> AI 整理 -> 闪卡 / 测试题 -> 成长问答。
重大技术边界、数据库表、API 命名、MVP 阶段取舍和最终验收仍然共同评审。
```

含义：

```text
1. 项目方向、MVP 边界和最终验收由两人共同决定。
2. 每个人主责一条可以独立跑通的功能闭环。
3. 陈要理解赵负责模块的接口和实现边界。
4. 赵要参与陈负责模块的体验、流程和验收判断。
5. 任何会影响周期或架构的变更，必须两人确认。
6. 主责不是独自完成；主责负责推进、产出草案和组织对方评审。
```

## 3. 阶段边界

当前项目按三段推进，避免第一版过大：

```text
MVP-0：静态 / 本地演示闭环
目标：用现有 app/ 原型讲清楚产品流程。
允许：localStorage、mock AI、单用户数据。

MVP-1：工程化最小版
目标：补前后端边界、数据库持久化、最小真实 AI 接口或可替换 AI mock 层。
重点：目标、资料、AI 整理、计划、打卡、进度这条主线。

MVP-2：完整化增强
目标：补注册登录、用户隔离、PDF 上传、部署和更完整测试。
```

默认规则：

```text
如果导师没有明确要求，MVP-1 不强行做完整登录、PDF 上传和正式部署。
```

## 4. 共同负责

以下内容不单独归某一个人：

```text
MVP 边界
核心用户场景
第一版功能优先级
接口字段确认
数据对象命名
导师待确认问题
最终演示流程
版本验收标准
```

共同讨论时优先回答：

```text
1. 这个功能是不是第一版必须做？
2. 它是否属于“目标 -> 资料 -> AI 整理 -> 计划 -> 打卡 -> 进度”主线？
3. 如果不做，会不会影响演示闭环？
4. 如果做，技术成本是否可控？
5. 是否可以先 mock，后续再真实实现？
```

## 5. 陈主责闭环

陈主责：

```text
目标管理 -> 行动计划 -> 今日任务 -> 打卡 -> 进度统计
```

重点职责：

```text
1. 梳理目标创建、编辑、计划生成、今日任务、打卡和进度查看的页面流程。
2. 维护 Goal、PlanTask、CheckInRecord、Progress 相关字段草案。
3. 准备演示时使用的示例目标、示例任务和用户故事。
4. 判断页面是否好懂、流程是否顺、反馈是否清楚。
5. 参与确认 API 字段是否能支撑页面展示。
```

陈重点关注：

```text
用户能不能看懂？
流程能不能一口气走完？
计划和打卡是否真的能推动用户继续使用？
进度展示是否有反馈感？
```

## 6. 赵主责闭环

赵主责：

```text
资料管理 -> AI 整理 -> 闪卡 / 测试题 -> 成长问答
```

重点职责：

```text
1. 设计 Material、MaterialSummary、Flashcard、QuizQuestion、AIConversation 等核心数据对象。
2. 梳理资料、AI 整理、闪卡、测试题和成长问答的 API 草案。
3. 选择技术栈并设计工程结构。
4. 接入或预留真实大模型接口。
5. 判断哪些功能先真实实现，哪些功能先 mock。
6. 维护 Git 协作、部署和本地开发方案。
```

赵重点关注：

```text
数据是否能保存和复用？
AI 输出是否可追踪、可展示、可失败兜底？
接口是否方便陈负责的页面流程调用？
第一版实现成本是否可控？
```

## 7. 分工表

| 工作内容 | 主责 | 协作方式 |
|---|---|---|
| 项目定位 | 共同 | 一起定，必要时问导师 |
| MVP 边界 | 共同 | 一起取舍，不单独决定 |
| PRD 和验收标准 | 陈主责 | 赵做技术可行性评估 |
| 技术实现方案 | 赵主责 | 陈确认是否支撑体验和演示 |
| 目标管理 | 陈主责 | 赵确认数据结构和接口 |
| 行动计划 | 陈主责 | 赵确认生成逻辑和实现成本 |
| 今日任务、打卡与进度 | 陈主责 | 赵确认持久化和统计逻辑 |
| 资料管理 | 赵主责 | 陈确认页面体验和使用场景 |
| AI 整理 | 赵主责 | 陈确认输出是否有用 |
| 闪卡 / 测试题 / 问答 | 赵主责 | 陈确认学习体验 |
| 数据模型和 API | 赵主责 | 陈确认字段是否满足页面 |
| Git 协作 | 赵主责 | 陈掌握基础流程并参与 PR / 合并 |
| 部署和测试环境 | 赵主责 | 陈参与验收体验 |
| Demo 演示 | 共同 | 陈主讲体验，赵补充技术实现 |

## 8. 第一阶段开发目标

第一阶段目标不是做一个完整大而全的 App，而是做出一个可以演示的最小可用版本。

优先跑通主线：

```text
目标 -> 资料 -> AI 整理 -> 计划 -> 打卡 -> 进度
```

第一阶段必须避免功能发散。新想法先记录，不直接加入当前版本。

## 9. 防止瓶颈规则

为避免赵变成所有技术问题的单点瓶颈，采用以下规则：

```text
1. 数据对象和 API 字段必须陈、赵共同评审后再实现。
2. 陈负责的页面流程必须写清楚输入、输出和验收标准。
3. 赵负责的技术方案必须写清楚哪些真实实现、哪些 mock。
4. 功能开发前先写 5-10 行接口草案，不直接开写大段代码。
5. 任一模块超过 1 天没有进展，先降级范围，不硬扛完整实现。
```

## 10. Git 分支规则

当前仓库固定使用 4 个协作分支：

```text
main                         稳定版本 / 最终演示版本
dev                          两人功能合并后的测试分支
feature/goal-plan-checkin    陈负责模块分支
feature/material-ai-memory   赵负责模块分支
```

分支职责：

```text
main：
只放测试通过、可以演示的稳定版本。

dev：
两个人的功能分支先合并到 dev，在 dev 上跑完整演示流程和联调测试。

feature/goal-plan-checkin：
陈使用，负责目标管理、行动计划、今日任务、打卡、进度统计。

feature/material-ai-memory：
赵使用，负责资料管理、AI 整理、闪卡、测试题、成长问答。
```

基本流程：

```text
1. 陈在 feature/goal-plan-checkin 开发并自测。
2. 赵在 feature/material-ai-memory 开发并自测。
3. 各自完成后先 push 到自己的 feature 分支。
4. 两个 feature 分支合并到 dev。
5. dev 上跑完整流程、修冲突、做联调测试。
6. dev 测试稳定后再合并到 main。
7. main 保持干净，只作为稳定演示版本。
8. main 上的重要版本再打 tag。
```

日常注意：

```text
1. 平时不要直接在 main 上开发。
2. 不要在自己的 feature 分支随意改对方主责模块，除非先沟通。
3. 改共享文档、公共字段和 API 草案时，要说明影响范围。
4. 每次开工先确认当前分支，避免把个人模块改到 main 或 dev。
5. 合并到 dev 前，至少完成一次本地自测。
```

## 11. Commit 提交规范

建议每次提交只做一类事情，提交信息尽量清楚。

推荐格式：

```text
feat: 添加目标管理功能
fix: 修复资料删除后闪卡未同步删除的问题
docs: 更新协作分工文档
style: 调整首页布局
refactor: 整理计划生成逻辑
test: 增加目标创建测试
```

常用类型：

```text
feat     新增功能
fix      修复问题
docs     文档修改
style    样式调整
refactor 代码重构
test     测试相关
chore    项目配置或杂项
```

## 12. 每周协作节奏

建议每周至少同步一次，每次控制在 30 分钟以内。

固定讨论 5 个问题：

```text
1. 这周完成了什么？
2. 当前卡在哪里？
3. 下周要做什么？
4. MVP 边界有没有变化？
5. 有没有需要问导师的问题？
```

同步结束后，要把结论写进任务清单或文档，不只停留在口头沟通。

## 13. 功能验收方式

每个功能完成后，至少按以下标准验收：

```text
1. 用户能不能正常完成这个操作？
2. 页面提示是否清楚？
3. 数据刷新后是否还在？
4. 删除、修改等危险操作是否有确认？
5. 出错时用户是否知道发生了什么？
6. 是否影响其他已有功能？
7. 是否仍然服务第一版主线？
```

## 14. 需求变更规则

早期项目一定会变，但不能每天随意改方向。

建议规则：

```text
1. 小文案、小样式可以直接调整。
2. 新增功能必须先写进 PRD 或任务清单。
3. 会影响开发周期的需求，需要陈、赵共同确认。
4. 已经开发中的功能，除非问题明显，否则不要频繁改目标。
5. 每次版本发布前冻结需求，只修问题。
```

## 15. 近期任务拆分

近期按 `docs/daily/2026-06-30工作安排.md` 作为日常开发分工主线：

```text
1. 陈推进：目标管理 -> 行动计划 -> 今日任务 -> 打卡 -> 进度统计。
2. 赵推进：资料管理 -> AI 整理 -> 闪卡 / 测试题 -> 成长问答。
3. 两人共同确认数据对象字段命名、API 返回格式和验收标准。
4. 先把当前 app/ 静态原型增强成可工程化业务原型。
5. 再评审 docs/planning/第一版技术实现方案.md 的 MVP-1A。
6. 确认后初始化 server/ 后端工程。
7. 把静态原型中的数据对象和 API 草案迁移到后端和数据库。
```

## 16. 当前建议

陈、赵不要把自己长期固定成“产品”和“技术”两个孤岛。更合适的协作方式是：各自主责一条功能闭环，同时共同参与边界、接口和验收。这样两个人都能理解项目全貌，也更适合后续汇报和导师追问。
