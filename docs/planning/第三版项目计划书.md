# 通用成长学习助手 App 第三版项目计划书

更新时间：2026-07-03

> 草稿来源：本计划书基于第二版计划书、第二版最终验收记录、真实模型联调记录、AI 问答接口交接、LLM Provider 设计说明、RAG chunks 接口说明和资料模块前后端接口对照整理。第三版不是从零起新方向，而是把第二版已经留下的增强线索收束成一个可开发、可验收的小版本。

## 1. 第三版总目标

第三版目标是把第二版“基于单份资料的 AI 问答与复习闭环”升级为“围绕成长目标的多资料学习推进闭环”。

第二版已经完成的主闭环是：

```text
资料录入
-> 资料摘要和练习生成
-> chunks 生成和关键词检索
-> 基于资料提问
-> 展示 answer / basis / suggestion / references / confidence
-> 保存并读回历史问答
-> 从历史问答生成复盘草稿
-> 用户确认加入正式闪卡
-> 闪卡 known / review 状态保存
-> 基础登录注册和用户数据隔离
```

第三版要在这个基础上补上三件事：

```text
1. 用户可以围绕一个成长目标检索和使用多份资料，而不是只能围绕单份资料提问。
2. AI 建议可以沉淀为待确认的复习或任务草稿，而不是停留在回答文本里。
3. 闪卡复习从简单状态升级为轻量复习日程，让“还要复习”有下一次行动。
```

第三版完成后的产品表达：

```text
第一版完成持久化学习闭环。
第二版完成基于资料的 AI 问答、历史读回和闪卡复盘闭环。
第三版完成围绕成长目标的多资料问答、复习日程和建议转行动草稿闭环。
```

## 2. 第三版要解决的用户问题

第二版里，用户已经可以问单份资料，但真实学习通常不是只看一份资料。

第三版要解决的问题：

```text
1. 用户围绕一个目标有多份资料时，不知道该从哪几份资料里找答案。
2. 用户希望问答历史能按目标聚合，而不是只散落在单份资料下面。
3. 用户希望 AI 建议能变成后续复习或任务草稿，而不是看完就忘。
4. 用户把问答转成闪卡后，希望系统提示哪些卡片该复习。
5. 用户希望 AI 回答更稳定地遵守结构化格式，减少模型自由发挥。
```

第三版核心用户故事：

```text
作为一个围绕成长目标学习的人，
我希望系统能在当前目标下检索多份资料并回答问题，
把可信回答和学习建议保存下来，
并允许我把建议转成复习卡片或待确认任务，
让资料学习、问答、复习和行动计划形成连续推进。
```

## 3. 第三版范围总览

第三版仍沿用第一版和第二版的两条业务链路，不按“前端 / 后端”重新切分。

```text
陈：目标推进链路 + AI 检索 / 问答后端底座 + 任务草稿联动
赵：资料学习链路 + 多资料学习入口 + 复习体验落地
共同：多资料问答规则、返回结构、复习日程字段、建议任务草稿验收
```

第三版包含四条主线：

```text
1. 多资料问答主线：按 goalId 检索当前目标下多份资料，返回跨资料 references。
2. 目标聚合主线：按目标查看相关问答、复习卡片和建议草稿。
3. 复习日程主线：闪卡从 new / known / review 状态升级为轻量 dueAt / reviewCount / lastReviewedAt。
4. AI 工程主线：收紧 Prompt、结构化输出解析，评估是否引入 LangChain 管理 Prompt 和输出格式。
```

第三版不是完整 RAG，也不是正式 Agent。

第三版合理定位：

```text
在第二版真实资料问答基础上，做“目标内多资料学习推进”，让 AI 回答能进入复习和行动计划的待确认流程。
```

## 4. 第三版最小产品闭环

第三版必须跑通的最小闭环：

```text
选择成长目标
-> 该目标下已有多份资料
-> 用户围绕目标提问
-> 系统从该目标下多份资料检索 chunks
-> AI 返回答案、依据、建议和跨资料引用
-> 问答记录按资料保存，同时能按目标聚合查看
-> 用户从回答生成闪卡或任务草稿
-> 用户确认后写入正式闪卡或任务
-> 闪卡根据轻量复习日程提示是否需要复习
```

这个闭环的关键不是“功能多”，而是让第二版的回答真正进入后续学习推进。

## 5. 第三版必做功能

### 5.1 多资料问答

目标：

```text
用户不指定 materialId、只指定 goalId 时，后端可以在当前目标下检索多份资料 chunks，并基于多个来源回答。
```

必做：

```text
1. POST /api/agent/ask 支持 goalId-only 问答。
2. materialId 为空、goalId 存在时，只检索该目标下资料。
3. references 可以来自多份资料。
4. basis 要说明主要依据了哪些资料。
5. sourceTitle 或 references 必须能展示多个资料标题。
6. 资料不足时继续返回 isFromMaterial=false 和 confidence=low。
7. 多资料回答仍要保存问答记录。
```

建议规则：

```text
1. 如果 materialId 存在，优先单资料问答。
2. 如果 materialId 为空但 goalId 存在，执行目标内多资料问答。
3. 如果 goalId 和 materialId 都为空，可以执行全局资料搜索，但第三版不把全局问答作为主验收路径。
```

### 5.2 按目标聚合问答历史

目标：

```text
用户可以在目标维度看到这个目标下发生过哪些资料问答和学习建议。
```

新增或候选接口：

```text
GET /api/goals/{goal_id}/qa
```

返回字段复用第二版 QA 结构：

```text
id
goalId
materialId
question
answer
basis
suggestion
sourceTitle
references
isFromMaterial
confidence
mode
createdAt
```

前端入口建议：

```text
1. 成长问答页：选择目标后展示目标相关历史问答。
2. 目标详情或进度页：展示最近问答、待复习卡片和建议任务草稿。
```

### 5.3 建议任务草稿

目标：

```text
AI suggestion 可以转成“待确认任务草稿”，用户确认后才写入正式 tasks。
```

边界：

```text
1. 第三版不允许 AI 自动修改计划。
2. 第三版不允许 AI 自动完成任务。
3. 第三版只做“生成草稿 -> 用户确认 -> 写入任务”。
```

建议数据形态：

```text
taskDraft = {
  id,
  goalId,
  materialId,
  qaRecordId,
  title,
  note,
  source,
  createdAt
}
```

建议接口：

```text
POST /api/goals/{goal_id}/tasks/drafts
GET  /api/goals/{goal_id}/tasks/drafts
DELETE /api/goals/{goal_id}/tasks/drafts/{draft_id}
POST /api/goals/{goal_id}/tasks/drafts/{draft_id}/confirm
```

如果第三版时间不够，可以先把任务草稿放在前端 localStorage，但正式验收更建议落后端，因为任务属于目标推进链路。

### 5.4 轻量复习日程

目标：

```text
闪卡不只保存 new / known / review，还能提示下一次应该什么时候复习。
```

建议扩展 flashcards 字段：

```text
status
reviewCount
lastReviewedAt
nextReviewAt
```

最小规则：

```text
1. 新卡 nextReviewAt 可以为空或当前时间。
2. 点击“已掌握”：status=known，reviewCount+1，nextReviewAt=当前时间+3天。
3. 点击“还要复习”：status=review，reviewCount+1，nextReviewAt=当前时间+1天。
4. 记忆页优先展示 nextReviewAt 已到期或 status=review 的卡片。
```

第三版不做复杂间隔重复算法。当前只做可解释、可测试的轻量规则。

### 5.5 Prompt 和结构化输出稳定性

目标：

```text
减少真实模型自由发挥，继续保证 answer / basis / suggestion / isFromMaterial / confidence 稳定返回。
```

必做：

```text
1. 保留 MockLLMProvider 作为默认测试基线。
2. OpenAI-compatible Provider 继续支持 backend/.env 和环境变量。
3. 真实模型失败时继续 fallback，不影响 smoke。
4. 三类问题样例继续作为回归基线：明确命中、部分命中、资料不足。
5. 针对多资料问答新增三类样例。
```

LangChain 的第三版定位：

```text
LangChain 可以作为 Prompt 模板和结构化输出解析工具进入第三版评估。
它不是第三版产品目标，也不做 LangChain memory、Agent executor 或多工具自动调用。
```

建议判断：

```text
如果直接 Provider + JSON parsing 已经稳定，第三版可以不接 LangChain。
如果 Prompt 模板和输出解析开始混乱，再引入 LangChain 做薄封装。
```

## 6. 第三版可选增强

如果必做功能提前稳定，可以选择：

```text
1. 问答质量反馈：有帮助 / 没帮助。
2. 多资料搜索结果页：按资料标题、chunk 命中数和 score 分组。
3. 将资料不足问题转为“补充资料提醒”草稿。
4. 目标进度中统计问答次数、复习卡片数、任务草稿确认数。
5. 给 QA 历史增加按 confidence / 是否资料不足筛选。
```

这些不作为第三版必过标准。

## 7. 第三版不做内容

为了避免第三版失控，明确不做：

```text
1. PDF 上传和解析。
2. Word / PPT / 图片 / 音视频解析。
3. 正式部署。
4. 复杂权限体系。
5. 多用户协作空间。
6. 向量数据库。
7. embedding 语义检索。
8. 完整 RAG 平台。
9. LangChain memory。
10. 真正 Agent 循环。
11. 多工具自动调用。
12. 自动联网搜索。
13. 自动大幅修改学习计划。
14. 复杂间隔重复算法。
15. 推荐系统。
```

## 8. 分支策略

当前仓库状态显示 `main` 已包含第二版发布合并，`origin/dev` 也保留第二版验收后的开发基线。第三版建议重新从 `dev` 或最新 `main` 拉出功能分支，避免直接在 main 开发。

建议：

```text
集成分支：dev
稳定分支：main
陈负责分支：feature/v3-goal-ai-loop
赵负责分支：feature/v3-material-review-loop
公共文档分支：可直接在 dev 或独立 docs 分支完成后合并
```

规则：

```text
1. 开始第三版前，先确认 main、dev 和 origin/dev 的关系。
2. 若 main 已领先 dev，先决定是否把 main 回合到 dev。
3. 功能开发不直接改 main。
4. 每个小闭环先在个人分支验收，再合 dev。
5. dev 通过 pytest、smoke、node --check 和浏览器主流程后，再判断是否合 main。
```

## 12. 验收标准

### 12.1 用户流程验收

```text
1. 可以选择一个成长目标。
2. 目标下至少有两份资料，并都能生成 chunks。
3. 用户在成长问答页只带 goalId 提问。
4. 系统能返回来自多份资料的 references。
5. 页面能清楚展示 answer、basis、suggestion、confidence 和多个来源资料。
6. 问答历史能按目标读回。
7. 用户能从问答生成闪卡草稿或任务草稿。
8. 用户确认后，闪卡或任务写入正式后端数据。
9. 闪卡复习后能更新 nextReviewAt。
10. 刷新页面后，上述数据仍能读回。
```

### 12.2 AI 可信度验收

保留第二版三类问题：

```text
1. 资料中有明确答案。
2. 资料中只有部分答案。
3. 资料中没有答案。
```

第三版新增多资料三类问题：

```text
1. 答案分散在两份资料中：AI 应引用两份资料。
2. 一份资料有答案、一份资料无关：AI 应主要引用相关资料。
3. 当前目标下资料都没有答案：AI 应说明资料不足。
```

### 12.3 工程验收

```text
1. python -m pytest backend/tests -v 通过。
2. python backend/smoke_api.py 通过，并包含多资料问答、目标 QA、闪卡复习字段。
3. node --check app/api.js app/app.js app/modules/chat.js app/modules/materials.js app/modules/goals.js app/modules/progress.js app/modules/utils.js 通过。
4. python -m compileall backend/app 通过。
5. 浏览器主流程无 console error / pageerror。
6. 默认 mock 基线不依赖真实 API Key。
7. 如果启用真实模型，只通过 backend/.env 或环境变量配置，不写入 Git。
```

### 12.4 协作验收

```text
1. 陈能说明多资料检索、目标 QA 聚合、任务草稿和 Provider 边界。
2. 赵能说明多资料问答入口、references 展示、复习日程体验和资料学习链路。
3. 双方共同确认第三版没有越界到 PDF、向量数据库、完整 RAG 或真正 Agent。
4. dev 集成后第一版和第二版主流程不回退。
```

## 14. 第三版演示脚本

```text
1. 登录或使用当前本地用户。
2. 创建或选择一个成长目标。
3. 在该目标下添加两份相关资料，并生成摘要、闪卡、测试题和 chunks。
4. 在成长问答页只围绕目标提问，不指定单份资料。
5. 展示回答引用了多份资料 references。
6. 提问一个目标资料中没有答案的问题，展示资料不足提示。
7. 从 AI suggestion 生成任务草稿。
8. 用户确认任务草稿，任务进入今日任务或目标任务列表。
9. 从 QA 生成闪卡，加入正式闪卡。
10. 点击“已掌握 / 还要复习”，展示 nextReviewAt 更新。
11. 刷新页面，展示问答、任务、闪卡复习状态仍可读回。
12. 说明第三版是在第二版基础上完成目标内多资料学习推进，而不是完整 RAG 或 Agent。
```

## 15. 风险和降级方案

### 15.1 多资料检索不准确

降级：

```text
先保持关键词检索，不上 embedding。
按 goalId 过滤后返回 top N chunks。
前端清楚展示 references，让用户能看见来源边界。
```

### 15.2 任务草稿影响目标主流程

降级：

```text
先做草稿，不自动写入任务。
确认按钮单独调用接口。
确认失败不影响原有 tasks。
```

### 15.3 复习日程规则争议

降级：

```text
只做 reviewCount、lastReviewedAt、nextReviewAt。
规则固定为 known +3 天、review +1 天。
复杂间隔重复算法放到后续版本。
```

### 15.4 LangChain 接入耗时

降级：

```text
继续使用 OpenAICompatibleLLMProvider。
只把 Prompt 模板和 JSON 解析整理清楚。
LangChain 写入后续增强，不阻塞第三版主闭环。
```

### 15.5 真实模型不稳定

降级：

```text
默认 mock 基线继续作为验收基础。
真实模型只作为人工联调记录。
失败、超时或解析失败继续 fallback。
```

## 16. 第三版完成后的项目表达

```text
项目第一版完成了 FastAPI + SQLite 的持久化学习助手 MVP。

系统能够围绕一个成长目标组织多份资料、回答问题、保留依据、提示资料不足，并把学习建议落到后续行动。
```
