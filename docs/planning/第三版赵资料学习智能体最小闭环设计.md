# 第三版赵资料学习智能体最小闭环设计

更新时间：2026-07-04

## 1. 结论

赵负责的第三版第一个最小开发闭环定义为：

```text
资料问答结果 -> 资料学习 Agent 判断 -> 结构化下一步动作 -> 复盘草稿 -> 用户确认写入正式记忆内容
```

这个闭环不重新做一套 Agent，也不改目标推进主流程。它只在第二版已经完成的资料问答、历史问答、复盘草稿和正式闪卡闭环上，补上第三版需要的结构化输出、资料不足判断和 AI 评估样例。

## 2. 为什么先做这个闭环

```text
为什么做：
第二版已经完成“资料问答 -> 历史问答 -> 复盘草稿 -> 正式闪卡 -> known / review 状态保存”。第三版第一步应该承接这个稳定闭环，而不是先做目标任务草稿、LangChain 或完整 Agent 循环。

练什么：
Prompt 约束、结构化输出设计、资料不足判断、AI 评估样例和资料到记忆的闭环设计。

怎么验：
用三类资料问答样例验证：资料有答案、资料部分有答案、资料无答案。每类样例都必须能推出明确的 confidence、nextAction 和 requiresConfirmation。

留什么证据：
本设计文档、后续接口草案、三类评估样例、pytest / smoke / 浏览器验收记录。
```

## 3. 不做范围

本闭环第一阶段明确不做：

```text
1. 不做 draft_tasks，不从 AI 建议写入目标任务。
2. 不改目标、计划、今日任务、打卡和进度主流程。
3. 不新增 GET /api/goals/{goal_id}/qa。
4. 不做目标内多资料问答。
5. 不接 LangChain。
6. 不做轻量复习日程。
7. 不自动写入正式闪卡、测试题或任务。
```

原因：

```text
为什么做：
先守住赵的资料学习链路，避免把第三版第一步扩大成陈的目标推进智能体链路。

练什么：
协作边界和最小闭环拆分。

怎么验：
代码改动范围后续应集中在资料问答输出、资料复盘草稿和资料链路展示，不触碰目标任务写入逻辑。

留什么证据：
PR 或提交说明中明确“未修改目标推进主流程”；验收命令保留第二版目标/任务/打卡 smoke 基线。
```

## 4. 继承第二版的数据流

当前第二版稳定数据流：

```text
资料页或成长问答页提问
-> app/api.js agentApi.ask()
-> POST /api/agent/ask
-> backend/app/routers/agent.py ask_agent()
-> backend/app/services/agent_service.py answer_question()
-> material_store.search_chunks()
-> llm_provider.generate_answer()
-> 返回 answer / basis / suggestion / references / isFromMaterial / confidence / mode
-> 如果有 materialId，保存 material_qa_records
-> GET /api/materials/{material_id}/qa 读回历史问答
-> 资料页从历史问答生成复盘草稿
-> 用户确认后 POST /api/materials/{material_id}/flashcards/custom
-> PATCH /api/materials/{material_id}/flashcards/{flashcard_id} 保存 known / review
```

第三版第一闭环只在返回结构和复盘草稿生成规则上增强：

```text
answer / basis / suggestion / references / confidence
+ nextAction
+ reviewDrafts
+ requiresConfirmation
+ insufficiencyReason
```

## 5. 最小输出结构

建议资料学习 Agent 输出结构：

```json
{
  "answer": "基于资料的回答，或资料不足说明",
  "basis": "回答依据，必须说明来自哪些资料片段或为什么资料不足",
  "suggestion": "学习建议",
  "references": [],
  "isFromMaterial": true,
  "confidence": "high",
  "mode": "mock",
  "nextAction": "create_flashcards",
  "reviewDrafts": [
    {
      "type": "flashcard",
      "front": "问题面",
      "back": "答案面",
      "source": {
        "type": "qa",
        "materialId": "material_xxx",
        "qaRecordId": "qa_xxx"
      }
    }
  ],
  "requiresConfirmation": true,
  "insufficiencyReason": ""
}
```

字段规则：

| 字段 | 第一闭环规则 |
|---|---|
| answer | 保留第二版回答字段；资料不足时必须明确说不足 |
| basis | 保留第二版依据字段；不能没有依据却写成高置信 |
| suggestion | 保留第二版建议字段；可以作为复习点来源 |
| references | 保留第二版引用片段；资料回答必须能追到片段 |
| confidence | high / medium / low |
| nextAction | 第一闭环只允许 answer_only、review_material、create_flashcards、create_quiz、ask_for_more_material |
| reviewDrafts | 只生成草稿，不自动写正式表 |
| requiresConfirmation | 只要 reviewDrafts 非空，必须为 true |
| insufficiencyReason | 资料不足时写明缺少什么，不足时不能留空 |

## 6. nextAction 最小决策规则

```text
answer_only：
资料能回答，但暂不需要生成复习内容。

review_material：
资料部分相关，但回答不完整；建议回看资料或补充复习点。

create_flashcards：
资料能明确回答，并且答案适合转换成问答式记忆卡。

create_quiz：
资料能明确回答，并且适合生成一道检查理解的测试题草稿。

ask_for_more_material：
没有 references，或 references 没覆盖问题关键概念；必须提示资料不足。
```

判断顺序：

```text
1. 先看 references 是否存在。
2. 再看问题关键概念是否能在 references 中找到依据。
3. 再看 confidence 是否能达到 high / medium。
4. 最后决定 nextAction。
```

关键约束：

```text
如果资料里没有答案，但模型凭常识能答出来，也不能标记为高置信资料回答。
正确结果应该是 confidence=low、isFromMaterial=false、nextAction=ask_for_more_material。
```

## 7. Prompt / 规则草案

第一闭环 Prompt 目标不是让模型更会聊天，而是让模型遵守资料边界和输出契约。

```text
你是资料学习智能体。你只能把给定资料片段中的信息作为资料结论。
如果资料片段不能支持用户问题，必须明确说明资料不足，不能用常识补全成资料依据。
请输出 JSON，不要输出 Markdown。

必须包含字段：
answer, basis, suggestion, references, isFromMaterial, confidence, nextAction, reviewDrafts, requiresConfirmation, insufficiencyReason

规则：
1. confidence 只能是 high、medium、low。
2. references 为空时，confidence 必须是 low。
3. references 没有覆盖问题关键概念时，confidence 必须是 low。
4. 生成任何草稿时，requiresConfirmation 必须是 true。
5. 不能自动写入正式闪卡、测试题或任务。
6. nextAction 只能从 answer_only、review_material、create_flashcards、create_quiz、ask_for_more_material 中选择。
```

## 8. 三类 AI 评估样例

### 8.1 资料明确包含答案

输入资料：

```text
RAG 会先根据用户问题检索相关资料片段，再把检索到的片段交给模型生成回答。回答必须引用资料来源，避免凭空编造。
```

用户问题：

```text
RAG 为什么能减少模型编造？
```

期望：

```text
confidence：high 或 medium
isFromMaterial：true
nextAction：create_flashcards 或 create_quiz
requiresConfirmation：true
insufficiencyReason：空
references：至少 1 条
```

为什么做：

```text
验证 Agent 能在资料足够时输出可复习动作，而不是只给一段回答。
```

练什么：

```text
结构化输出和资料到记忆的动作设计。
```

怎么验：

```text
检查 answer / basis 是否能被 references 支撑，reviewDrafts 是否能转成复盘草稿。
```

留什么证据：

```text
评估样例结果、接口返回 JSON、后续浏览器截图。
```

### 8.2 资料只包含部分答案

输入资料：

```text
RAG 使用检索片段辅助回答。系统会保存资料问答历史，方便后续复盘。
```

用户问题：

```text
RAG 和 LangChain memory 有什么区别？
```

期望：

```text
confidence：medium 或 low
isFromMaterial：false 或部分说明
nextAction：review_material 或 ask_for_more_material
requiresConfirmation：false，除非只生成“复习资料中已有内容”的草稿
insufficiencyReason：说明资料没有覆盖 LangChain memory
references：可以有，但不能支撑完整问题
```

为什么做：

```text
验证 Agent 不会把“部分相关”误判成“完整回答”。
```

练什么：

```text
资料不足边界判断。
```

怎么验：

```text
检查回答是否明确区分“资料提到了 RAG”与“资料没有说明 LangChain memory”。
```

留什么证据：

```text
部分答案样例记录，作为真实模型回归检查用例。
```

### 8.3 资料完全无答案

输入资料：

```text
这份资料介绍如何把历史问答转换成闪卡，并保存 known / review 状态。
```

用户问题：

```text
Transformer 的多头注意力公式是什么？
```

期望：

```text
confidence：low
isFromMaterial：false
nextAction：ask_for_more_material
requiresConfirmation：false
reviewDrafts：[]
insufficiencyReason：资料未提及 Transformer、多头注意力或公式
references：可以为空；即使命中弱相关片段，也不能高置信
```

为什么做：

```text
验证 Agent 在资料不足时不编造，这是第三版可信度底线。
```

练什么：

```text
AI 安全输出、资料不足判断和评估样例设计。
```

怎么验：

```text
检查返回是否明确提示补充资料，而不是回答公式。
```

留什么证据：

```text
无答案样例记录，可用于 MockLLMProvider 和真实 Provider 的共同验收。
```

## 9. 后续实现顺序建议

### 第一步：只补接口契约和样例

```text
为什么做：
先让赵能说清楚输出结构和资料不足规则，再写代码。

练什么：
接口契约、AI 评估样例。

怎么验：
三类样例都有明确期望字段，陈能看懂边界，不影响目标推进链路。

留什么证据：
本设计文档和后续接口交接文档。
```

### 第二步：Mock 输出先遵守结构

```text
为什么做：
默认测试和 smoke 不能依赖真实 API Key，所以 Mock 必须先稳定。

练什么：
mock AI 输入输出形状、可回归设计。

怎么验：
pytest 覆盖 nextAction、requiresConfirmation、资料不足 low confidence。

留什么证据：
backend/tests 中的三类样例测试。
```

### 第三步：真实 Provider Prompt 对齐

```text
为什么做：
真实模型可以换，但输出契约不能变。

练什么：
Prompt 约束和真实模型替换边界。

怎么验：
智谱 glm-4-flash-250414 复跑三类样例，默认测试仍走 mock fallback。

留什么证据：
真实模型联调记录追加第三版样例结果，不记录 API Key。
```

### 第四步：前端展示 nextAction 和草稿

```text
为什么做：
用户要看见“AI 建议下一步做什么”，但正式写入仍需确认。

练什么：
资料学习链路体验和确认写入边界。

怎么验：
浏览器流程：问答 -> 看到 nextAction -> 生成复盘草稿 -> 用户确认加入正式闪卡 -> 刷新读回。

留什么证据：
浏览器验收记录和截图。
```

## 10. 验收清单

第一闭环完成时必须满足：

```text
1. 保留第二版 answer / basis / suggestion / references / confidence / mode 字段。
2. 新增或规划 nextAction、reviewDrafts、requiresConfirmation、insufficiencyReason。
3. 三类评估样例均有明确期望输出。
4. 资料不足时不能高置信，也不能生成正式写入。
5. 草稿类输出必须 requiresConfirmation=true。
6. 正式闪卡 / 测试题仍由用户确认后写入。
7. 不修改目标推进主流程。
8. 默认 pytest / smoke 仍不依赖真实 API Key。
9. 第二版资料问答 -> 历史问答 -> 复盘草稿 -> 正式闪卡 -> known / review 基线不被破坏。
```

建议验证命令：

```bash
python -m pytest backend/tests -v
python backend/smoke_api.py
python -m compileall backend/app
node --check app/api.js app/app.js app/modules/chat.js app/modules/materials.js app/modules/goals.js app/modules/progress.js app/modules/utils.js
```

浏览器验收：

```text
资料 -> 生成 chunks -> 问 AI -> 历史问答读回 -> 复盘草稿 -> 加入正式闪卡 -> known / review 保存 -> 刷新读回
```
