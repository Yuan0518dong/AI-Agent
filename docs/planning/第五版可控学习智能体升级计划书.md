# 第五版可控学习智能体升级计划书

更新时间：2026-07-08

## 1. 第五版定位

第五版目标不是继续堆普通业务功能，而是把 AI-Agent 从“可控学习智能体闭环 MVP”升级为更完整的垂直学习 Agent。

项目定位：

```text
AI-Agent：面向学习规划场景的可控 AI Agent。
```

第五版强调四个关键词：

```text
可观察：统一读取目标、任务、资料、问答、复习、测试和反馈历史。
可决策：输出结构化下一步动作，而不是只做自然语言问答。
可执行：通过工具草稿把建议接入真实学习流程。
可追踪：记录每轮运行、用户反馈、执行结果和下一轮状态变化。
```

第五版仍然不做通用 Agent 平台，不做 AutoGPT 式无限循环，不让模型绕过用户确认直接改学习计划。

一句话目标：

```text
用几天时间把“能给建议的学习系统”升级为“有运行轨迹、有工具边界、有反馈记忆、可用真实模型增强的可控学习 Agent”。
```

## 2. 为什么继续做这个方向

当前项目已经具备第四版闭环基础：

```text
AgentContext：读取学习状态。
AgentDecision：生成结构化建议。
AgentActionLog：记录采纳、忽略、稍后、执行。
草稿态执行：先生成草稿，再由用户确认写入。
上下文回读：写入后下一轮 Agent 能看到状态变化。
```

继续做第五版的价值在于：

```text
1. 项目从“AI 问答 + 学习管理”升级为“有运行生命周期的 Agent 系统”。
2. 简历可以重点讲 Agent 状态、决策、工具、确认、反馈和验证，而不是只讲调用大模型 API。
3. 适合 AI 应用开发、大模型应用工程、AI Agent 工程、后端 + AI 应用等岗位。
4. 几天时间内可以做出可验证的系统化提升，不需要换项目重开。
```

## 3. 第五版核心目标

第五版要形成一条更清晰的 Agent 生命周期：

```text
AgentRun 开始
-> 读取 AgentContext
-> 生成 AgentDecision
-> 选择 ToolPlan
-> 记录 ActionLog
-> 用户采纳 / 忽略 / 稍后 / 执行
-> 生成草稿或跳转处理入口
-> 用户确认写入
-> 下一轮 Context 回读
-> AgentRun 总结与反馈记忆
```

验收标准不是“功能更多”，而是：

```text
同一个学习状态下，Agent 能解释为什么做这个建议。
用户反馈后，下一轮 Agent 不会机械重复。
每个建议能落到明确工具、风险等级和确认流程。
真实模型输出不稳定时，系统仍能回退到稳定规则决策。
每个关键场景都有自动化测试或 smoke 证据。
```

## 4. 优先级判断

第五版按“简历价值 / 工程风险 / 时间成本”排序，不按功能数量排序。

必须做：

```text
1. Feedback Memory：让 Agent 记住用户采纳、拒绝、稍后和执行状态。
2. AgentRun：让每次智能体运行有可追踪生命周期。
3. Tool Registry：让动作从散落字符串变成有风险等级和确认规则的工具。
4. Evaluation Scenarios：让四类场景有测试和 smoke 证据。
```

尽量做：

```text
1. LLM JSON Decision hybrid：真实模型结构化决策 + rule-based 兜底。
2. 前端工作台展示 AgentRun、Tool 风险和反馈记忆。
3. README 和简历文档同步第五版成果。
```

可以后置：

```text
1. 定时自动运行 Agent。
2. 多轮自动循环。
3. 向量数据库和语义召回。
4. PDF 上传解析。
5. GitHub Actions 和正式部署。
```

判断方法：

```text
如果一个改动不能增强“观察 -> 决策 -> 工具 -> 反馈 -> 回读”的闭环，就不要放进第五版主线。
如果一个改动会让模型绕过用户确认直接写库，就不做。
如果一个改动没有办法用测试或 smoke 证明，就先缩小范围。
```

## 5. 模块规划

### 5.1 AgentRun：智能体运行轨迹

新增 AgentRun，用来记录一次完整智能体运行。

推荐字段：

```text
agent_runs
- id
- user_id
- goal_id
- trigger: manual / after_write / scheduled
- context_snapshot
- decision_snapshot
- feedback_summary
- status: created / decided / feedback_recorded / executed / closed
- created_at
- updated_at
```

接口建议：

```text
POST /api/agent/runs
GET /api/agent/runs?goalId=...&limit=...
GET /api/agent/runs/{run_id}
PATCH /api/agent/runs/{run_id}
```

列表接口建议只返回摘要：

```text
id
goalId
trigger
status
contextSummary
decisionSummary
feedbackSummary
createdAt
updatedAt
```

详情接口再返回 context_snapshot 和 decision_snapshot。这样既能保留完整运行证据，也不会让工作台列表一次读取过大的 JSON。

第一阶段只做最小闭环：

```text
1. 点击“生成建议”时创建 AgentRun。
2. AgentRun 保存 context 和 decision 快照。
3. 用户记录 ActionLog 后，AgentRun 能读到反馈概览。
4. 工作台展示最近运行轨迹。
```

不做：

```text
不自动后台运行。
不做多轮无限循环。
不把完整大对象无限累积到前端 localStorage。
```

### 5.2 Tool Registry：工具注册与风险分层

把当前 proposedAction 对应的能力整理成工具注册表。

推荐工具：

```text
review_material：进入资料整理或复习入口。
create_review_draft：生成复盘/闪卡草稿。
create_task_draft：生成任务草稿。
suggest_material_gap：生成补资料建议。
answer_only：只给学习建议，不写入。
```

每个工具定义：

```text
name
label
description
inputSchema
outputType
riskLevel: low / medium / high
requiresConfirmation
draftOnly
applyTarget
```

建议第一版工具表：

```text
review_material
- riskLevel: low
- draftOnly: false
- applyTarget: materials
- 行为：跳转资料/复习入口，不直接写库。

create_review_draft
- riskLevel: medium
- draftOnly: true
- applyTarget: review_drafts
- 行为：生成复盘或闪卡草稿，用户确认后才写正式 flashcards。

create_task_draft
- riskLevel: high
- draftOnly: true
- applyTarget: task_drafts
- 行为：生成任务草稿，用户确认后才复用现有计划生成流程。

suggest_material_gap
- riskLevel: medium
- draftOnly: true
- applyTarget: materials
- 行为：预填补充资料表单，用户保存后才写 materials。

answer_only
- riskLevel: low
- draftOnly: false
- applyTarget: study
- 行为：只给学习建议或跳转问答页。
```

原则：

```text
低风险：跳转、只读提示，可以直接执行或标记 applied。
中风险：生成草稿，但不写入正式表。
高风险：修改任务计划、创建正式复习内容，必须用户确认。
```

第一阶段可以先做后端静态 registry，不急着完全迁移前端执行逻辑。

与当前 proposedAction 的兼容映射：

```text
review_material -> review_material
create_flashcards -> create_review_draft
create_quiz -> create_review_draft
reschedule_tasks -> create_task_draft
create_followup_tasks -> create_task_draft
ask_for_more_material -> suggest_material_gap
answer_only -> answer_only
```

第五版第一阶段不要急着把前端所有 actionType 改名。更稳的做法是保留现有 actionType，对外增加 toolName / riskLevel / draftOnly / applyTarget 字段。

### 5.3 LLM JSON Decision：真实模型结构化决策

当前 AgentDecision 是 rule-based，适合稳定验收。第五版可以增加 LLM 决策增强层。

推荐结构：

```text
decision_mode=rule-based：默认稳定模式。
decision_mode=llm-json：真实模型输出结构化 JSON。
decision_mode=hybrid：LLM 输出建议，规则校验和兜底。
```

LLM 输出必须符合 schema：

```text
stateSummary: string
problems: array
nextAction: string
reason: string
requiresConfirmation: boolean
proposedActions: array
reflection: string
```

建议增加校验后的统一字段：

```text
mode: rule-based / llm-json / hybrid
fallbackReason: string
toolValidationErrors: array
confidence: low / medium / high
```

安全边界：

```text
1. JSON 解析失败，回退 rule-based。
2. actionType 不在 Tool Registry 中，回退 rule-based。
3. 高风险动作必须 requiresConfirmation=true。
4. LLM 不能直接写 tasks、flashcards 或 materials。
5. 测试默认使用 mock/rule-based，真实模型只做联调和 smoke。
```

### 5.4 Feedback Memory：反馈记忆与策略调整

当前已开始让 AgentDecision 读取 ActionLog，识别：

```text
pendingAccepted：用户已采纳但未执行。
recentlyRejected：用户刚拒绝过。
deferred：用户选择稍后。
applied：用户已执行。
```

第五版继续增强：

```text
1. 工作台显式展示反馈记忆。
2. AgentRun 汇总本轮反馈。
3. 连续拒绝同类动作时，Agent 给出替代策略。
4. applied 后下一轮优先检查上下文是否真的变化。
```

示例：

```text
如果用户连续拒绝 create_flashcards，Agent 不再重复要求生成闪卡，改为建议先完成一次现有卡片复习或补资料。
如果用户 accepted 但未 applied，Agent 提醒先处理已采纳建议，而不是创建重复建议。
```

### 5.5 Evaluation Scenarios：可演示验收场景

第五版必须沉淀可复现验收场景，而不是只靠口头说明。

建议至少保留 4 个：

```text
1. 任务逾期：Agent 发现进度滞后，建议生成任务草稿或重排。
2. 测试薄弱：Agent 发现 quiz weak attempts，建议生成复习草稿。
3. 资料不足：Agent 发现资料无法支撑回答，建议补充资料。
4. 反馈记忆：用户拒绝或稍后某动作后，下一轮 Agent 改变建议顺序或避免重复。
```

每个场景保留：

```text
初始数据
AgentContext 摘要
AgentDecision 输出
ActionLog / AgentRun 记录
用户确认写入后的下一轮回读结果
测试或 smoke 输出
```

## 8. 技术边界

第五版不做：

```text
1. 不做通用多 Agent 协作平台。
2. 不做自动无限循环执行。
3. 不让 LLM 直接写正式任务或正式闪卡。
4. 不在几天内重构为向量数据库。
5. 不把评估重点放在模型回答是否华丽，而放在闭环是否可控、可追踪、可验证。
```

第五版必须坚持：

```text
1. 所有高风险写入先生成草稿。
2. 用户确认后再进入正式数据。
3. 每次关键改动都补测试或 smoke。
4. mock 基线必须稳定。
5. 真实模型能力作为增强，不作为测试依赖。
```

## 9. 验证矩阵

每个批次至少保留一种可复现证据：

```text
Feedback Memory
- pytest：拒绝后不重复；采纳未执行会被记忆。
- smoke：输出 feedbackMemory 关键信号。

AgentRun
- pytest：create / list / get / update；goalId 过滤；user isolation。
- smoke：输出 run 数量、最新 run 状态。

Tool Registry
- pytest：所有 actionType 合法；非法 action 回退；高风险必须确认。
- node --check：前端展示不破坏。

LLM JSON Decision
- pytest：mock JSON 成功、非法 JSON 回退、非法 tool 回退。
- 人工 smoke：真实模型输出结构化 decision。

Evaluation Scenarios
- docs：四类场景有输入、输出、反馈、回读。
- smoke：至少覆盖反馈记忆和确认写入后的下一轮回读。
```

## 10. 风险与取舍

主要风险：

```text
1. 做成“功能很多但不像 Agent”：用 AgentRun 和 Tool Registry 收束。
2. LLM 决策不稳定：默认 rule-based，LLM 只做 hybrid 增强。
3. 自动执行破坏用户计划：所有高风险动作 draftOnly + requiresConfirmation。
4. 文档和代码脱节：每批完成后同步 README / 当前状态 / 验收样例。
5. 时间被 PDF、部署、向量库带偏：这些放到第五版之后。
```

取舍原则：

```text
宁愿做少一点，但每个闭环可测试、可演示、可解释。
宁愿保留 rule-based 兜底，也不要让真实模型成为测试不稳定源。
宁愿先做草稿态执行，也不要追求自动替用户完成所有动作。
```

## 11. 简历表达目标

第五版完成后，项目可以这样表达：

```text
设计并实现面向学习规划场景的可控 AI Agent，构建 AgentContext、AgentDecision、AgentRun、Tool Registry 与 ActionLog 机制，实现学习状态感知、结构化决策、工具草稿执行、用户确认写入、反馈记忆和下一轮上下文回读；支持 mock / OpenAI-compatible Provider 切换，并通过 pytest 与 smoke 场景验证核心闭环稳定性。
```

可拆成亮点：

```text
1. 设计 Agent 生命周期：观察、决策、工具计划、反馈、执行、回读。
2. 抽象学习工具注册表，按风险等级控制是否直接执行或进入草稿确认。
3. 引入 ActionLog 和 Feedback Memory，避免 Agent 重复推荐用户已拒绝动作。
4. 支持 LLM JSON 结构化决策，并提供规则兜底保障稳定性。
5. 使用 pytest 和 smoke 验证任务逾期、测试薄弱、资料不足、反馈记忆等场景。
```
