# 个人学习助手后续任务执行文档

更新时间：2026-07-22

## 文档定位

本文档是项目后续开发的唯一任务入口。项目不再按“第几版”组织，而是用 3 至 4 周完成面向 Agent / AI 应用开发实习的最终工程收口。

执行目标不是把个人项目长期扩建成商业平台，而是形成一个可部署、可演示、可量化、可深入面试的个人学习 Agent。求职投递与项目收口并行，不等待本文全部完成后再开始投递。

## 项目目标

项目继续定位为“基于可控 Agent 的个人学习助手”，核心闭环固定为：

```text
学习目标
-> 资料摄取与带引用问答
-> 测验发现薄弱点
-> Agent生成复习草稿
-> 用户确认
-> 闪卡进入间隔复习
-> 今日建议随学习结果变化
```

对外重点同时保留两层价值：

- 用户价值：知道下一步学什么、为什么这样安排、学习后发生什么变化。
- 工程价值：可恢复 Agent Runtime、工具约束、高风险确认、RAG、真实模型评测和可复现证据。

## 当前已具备的基线

以下能力已经完成，只在后续回归中验证，不再作为新功能重复实施：

- 目标、任务、打卡、进度、资料、问答、闪卡和测试基础链路。
- PDF、Markdown、TXT 内存式摄取和 PostgreSQL/pgvector 混合检索。
- 问答引用已经包含资料名、页码或标题路径、原文片段和检索分数。
- Agent Runtime、AgentStep、Decision Guard、草稿确认、恢复、幂等和取消。
- 普通 Agent 执行已经要求选择目标；模型模式和技术运行信息已经默认折叠。
- 新用户空状态、一键 Demo、移动端五项导航、桌面/390px Playwright 和公开 Mock Demo。
- A3 真实 20 场景 x 3 评测：系统工具选择 `0.8833`、确认完整性 `0.7778`、恢复 `1.0`，67 次 Provider 请求，估算成本 `$0.017471`。

借鉴原则：只吸收能改善“目标 -> 学习 -> 测验 -> 复习 -> 调整”闭环，且能在 4 周内由个人维护、测试和解释的机制；不以竞品功能数量作为项目完成标准，也不复制其代码、导航数量、品牌表达或产品角色设定。

命名边界固定为：产品品牌使用“成长学习助手”，项目定位使用“基于可控 Agent 的个人学习助手”，Agent 功能模块使用“智能助手”。“教练式建议”只能描述一种交互方式，不能替换产品、项目或模块名称；“空间/Workspace”只能作为通用技术概念，不能替换“学习目标”这一核心业务对象。

## 时间与停止规则

```text
第1周：Agent可靠性收口
第2周：错题与间隔复习
第3周：学习闭环界面整合
第4周：自动化、求职材料和部署收口
```

预计总量为 15 至 18 个有效工作 Block；按每天稳定投入 2 至 4 小时计算，3 至 4 周可完成。求职投递和基础学习继续并行，不能因为项目任务顺延而暂停。

执行约束：

1. 总投入最多 4 周；每周只处理对应任务，不向后续阶段扩散。
2. 每个任务必须同时交付代码、测试和用户可见结果，只有代码不算完成。
3. 真实 Provider 最多再执行一轮固定 20 x 3 评测，且必须重新获得费用授权。
4. 最终评测未达到质量目标时，记录真实结果并停止调参，不继续创建 A5、A6 式候选。
5. 第 4 周结束后项目进入维护状态，只修缺陷和更新求职材料。

任务优先级：

- P0：全部 `REL`、全部 `LOOP`、`UX-03` 和全部 `CLOSE`，构成可运行、可评测的学习闭环。
- P1：`UX-01/02/04`，用于减少界面割裂；如果 4 周工期不足，只做文案和入口收敛，不扩大为页面重构。

## 阶段价值与证据

| 阶段 | 用户结果 | 训练能力 | 必须留下的证据 | 面试可讲问题 |
|---|---|---|---|---|
| `REL` | Agent 不再选含义重叠动作，确认与回滚边界明确 | 接口契约、状态机、安全 Guard、评测设计 | PR diff、兼容测试、corrected 报告、失败分类 | 为什么缩小模型责任比继续堆 Prompt 更可靠 |
| `LOOP` | 错题能进入复习，闪卡按记忆状态再次出现 | 第三方库选型、双数据库迁移、事务和数据一致性 | Alembic、SQLite 探针、API 测试、调度样例 | 为什么使用 FSRS，以及如何防止状态漂移和历史丢失 |
| `UX` | 用户能看懂下一步学习行动和原因 | 信息架构、确定性推荐、响应式交互 | 桌面/移动截图、Provider 0 请求断言 | 如何把技术型 Agent Runtime 转成可用学习产品 |
| `CLOSE` | 完整闭环可复现、可部署、可核验 | E2E、CI、部署、指标披露和技术表达 | Playwright、CI 链接、公开 Demo、README、简历 Bullet | 如何区分 Mock、真实模型、系统指标和安全结论 |

价值判断规则：不能改变用户结果、不能训练目标岗位需要的能力、也不能留下可验证证据的任务，不进入 P0；仅改善装饰或增加热点名词的功能直接延后。

可靠性质量目标：

```text
corrected suite系统工具选择成功率 >= 0.85
corrected suite确认完整性 >= 0.85
恢复成功率 = 1.0
Guard召回 = 1.0
```

质量目标用于衡量效果，不再作为无限期不合并的唯一条件。允许进入合并审批的安全门槛是：全量 CI 通过、高风险写入不能绕过确认、Guard 和恢复保持 `1.0`、没有相对 A3 的安全回归，并完整披露未达指标。合并仍需用户明确授权。

评测披露规则：

- `legacy suite` 保留 A0/A2/A3 原始 fixture、报告和指标，只用于解释历史演进。
- `corrected suite` 使用规范动作与显式确认/回滚契约，作为当前实现的工程验收。
- 两套 fixture 不相同时，不把 corrected 指标直接接到 A0/A2/A3 曲线上宣称“同一评测集提升”；除非未来对所有历史提交重新运行 corrected suite，本轮不承担该成本。

## 第 2 周：错题与间隔复习

- [x] `LOOP-01` 引入 MIT 许可的 `fsrs==6.3.1`，使用 `desired_retention=0.9`、`maximum_interval=365`、`enable_fuzzing=false` 和 UTC 时间；删除原任务书自定义的 `1.2/2.3/3.0` 复习倍率方案。
- [x] `LOOP-02` SQLite 和 PostgreSQL 的 `flashcards` 增加 `fsrs_card`、`due_at`、`last_reviewed_at`、`review_count`、`last_rating`，为 `due_at` 建索引；`fsrs_card` 使用 JSON 文本以保持双数据库一致。`fsrs_card` 是调度事实来源，`due_at` 必须始终等于反序列化后的 `Card.due`，两者在同一事务写入。旧卡因没有可信复习历史统一初始化为立即到期，不伪造间隔。
- [x] `LOOP-03` 建立唯一的 Flashcard Review Service 和 `new_scheduled_flashcard()` 工厂。资料批量生成、手工创建、Agent 草稿确认、Demo 种子和旧状态兼容接口均通过该服务写入；账户导出和读取映射包含新调度字段。`retrievability` 请求时从 `fsrs_card` 计算，不持久化；反序列化失败返回 `409 flashcard_schedule_invalid` 并保留原状态，不静默重置学习历史。
- [x] `LOOP-04` 新增跨资料到期队列和 Again / Hard / Good / Easy 四档评级，新界面只使用 FSRS 评级。旧状态接口仍保留，但 `known` 委托同一服务执行 `Good`，`review` 执行 `Again`；`new` 只允许 `reviewCount=0` 时幂等保持，已复习卡请求重置返回 `409`。兼容调用也必须原子更新 `status/fsrs_card/due_at/review_count/last_rating`。
- [x] `LOOP-05` 按 `quizId` 从现有答题记录派生薄弱点，不新增薄弱点表；最新一次错误或分数低于 70 为未解决，后续正确且不低于 70 后自动解决。已有答题记录时，重新生成测试题必须返回 `409 quiz_history_exists`，不得通过删除旧题级联删除错题历史；本轮不提供破坏性重置接口。
- [x] `LOOP-06` Agent Context 读取到期闪卡和未解决薄弱点；用户从薄弱点生成闪卡复习草稿后，仍须确认才能写入正式闪卡。重做测试继续走已有测试页面，不新增测试题草稿写入。

智能助手默认区从当前 Run/最新 Step 的既有快照中提取行动、原因和学习依据，不在加载时生成新 Decision。按钮必须按动作合同展示：`apply_confirmed_draft` 只提供“接受”和“拒绝”两个状态转换；“暂不处理”只能关闭或离开当前提示，不调用状态更新接口，也不得伪装为持久化业务状态。普通建议只使用其现有合法反馈状态，不能把所有动作强行合并为同一三按钮状态机。Run 状态、模式、Guard 结果和是否等待确认紧凑可见；Decision、Tool I/O、Token、fallback、Step 时间线和原始 JSON 保留在默认关闭的技术详情中。

## API 与数据契约

### Agent 动作

新模型动作：

```json
{
  "type": "create_review_draft",
  "payload": {
    "materialIds": ["material_id"]
  }
}
```

`materialIds` 必填、不能为空、必须去重并全部属于当前用户和目标。`weakAttemptCount` 只保留在 Agent Context 中，不进入模型动作载荷。该动作只表示创建闪卡复习草稿；历史动作在 Guard 入口归一化为该结构，新决策不再输出历史动作名称。执行器在任何情况下生成 0 条草稿都必须失败，不能记录成功 Step。

本轮不新增测试题草稿类型、确认应用逻辑或 `format=quiz`。用户需要检查掌握程度时进入现有测试页面，Agent 可以解释原因和提供入口，但不能声称已经创建待确认测试题。

### 复习接口

```text
GET /api/review/queue?goalId=...
GET /api/review/weak-points?goalId=...
POST /api/materials/{material_id}/flashcards/{flashcard_id}/reviews
```

评级请求：

```json
{"rating": "again|hard|good|easy"}
```

评级响应：

```text
flashcardId
status
dueAt
lastReviewedAt
reviewCount
lastRating
retrievability: float | null
```

调度一致性：

- `fsrsCard` 是事实来源，`dueAt` 是用于数据库查询的索引投影。
- 每次评级后必须验证 `dueAt == Card.from_json(fsrsCard).due`。
- `retrievability` 只在响应时计算；新卡或无法计算时返回 `null`。
- FSRS JSON、`dueAt`、兼容 `status` 和计数在同一事务提交或回滚。

薄弱点响应：

```text
quizId
question
materialId
materialTitle
wrongCount
latestScore
latestFeedback
latestAttemptAt
resolved
```

测试题生成保护：

```text
POST /api/materials/{material_id}/quiz
```

- 没有答题记录时保持现有生成和替换行为。
- 已经存在任意答题记录时返回 `409 quiz_history_exists`，保留题目、答案和全部 attempts。
- 用户通过现有题目重做来解决薄弱点；本轮不增加删除历史或强制重置参数。

本轮不新增 `/api/goals/{goal_id}/workspace`。学习目标快捷入口复用现有目标、资料、问答、复习和进度接口；Today 如需新增读取，只允许有界行动投影，不复制完整 Agent Context 或资料正文聚合。
