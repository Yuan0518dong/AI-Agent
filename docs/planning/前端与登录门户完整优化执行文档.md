## 1. 文档定位

本文档是 AI-Agent 项目前端与登录门户完整优化的唯一执行清单，可直接作为后续 Goal 模式的任务依据。

本轮工作的目的，是在保持现有产品能力和后端契约不变的前提下，系统优化登录门户和全部现有前端视图。最终界面既要适合日常使用，也要让公司上司、招聘者和面试官能够在本地快速看懂、稳定操作和复核 FastAPI、Agent Runtime、RAG、确认式写入、FSRS 与工程化能力。

这不是只修当前两个测试问题的短期收口。`FE-00` 完成后，继续依次执行 `FE-01` 至 `FE-07`；允许完整调整现有页面的布局、视觉层级、文案、响应式和前端交互状态，但不借机增加后端能力或新产品功能。本计划不设置统一完成天数，以阶段门禁和可验证结果控制质量；需要暂停时只能停在已通过门禁的阶段边界。

项目继续保持以下事实边界：

- 这是维护者在实习期间持续参与并最终负责推进的唯一项目，也是可以公开展示的个人作品。
- V1-V2 为双人协作，V3 按方向分工，V4 起由维护者独立推进新增架构、工程化、评估和发布；不得表述为“从零独立完成全部版本”。
- 前端采用 HTML、CSS 和原生 JavaScript；本轮不迁移 React、Vue 或其他框架。
- 当前产品能力和指标以现有验收报告、测试、提交与截图为准；计划中的界面、测试和性能改进不能提前写入简历。

## 2. 优化目标与项目边界

### 2.1 展示目标

本项目主要服务于以下求职展示方向：

1. AI 应用开发、智能体应用、知识库、RAG 与知识图谱方向。
2. 后端或平台研发、企业数字化与企业信息系统研发方向。

本项目不以纯前端岗位、纯数据工程岗位、模型训练岗位或通用基础设施岗位为主要目标。前端优化的作用，是让既有后端、数据、Agent 和 RAG 能力更容易被看见和讲清，而不是改变项目的技术身份。

因此，本轮前端优化只承担三个职责：

- 让非项目成员在 90 秒内看懂“学习闭环、RAG 引用、Agent 确认、安全边界”四项核心价值。
- 让技术面试官可以顺着界面追问后端架构、数据流、状态机、测试和工程取舍。
- 让本地演示在网络较慢或在线服务冷启动时仍然可用。

### 2.2 本轮授权边界

- 项目状态：`v7.1.0` 的产品功能、后端接口、数据库结构和评测口径继续冻结。
- 本轮例外：重新开放前端展示层，完整执行 `FE-00` 至 `FE-07`，覆盖登录门户和所有现有业务页面。
- 允许结果：现有能力的布局、视觉系统、交互反馈、可访问性、响应式和演示材料可以发生明显变化。
- 禁止结果：不能因界面需要而新增 API、数据库字段、业务状态、模型能力或产品模块。
- 停止规则：`FE-07` 通过最终门禁后重新冻结；此后除 P0 缺陷或黄金演示路径内可复现的 P1 外，不继续美化或扩展页面。

## 5. 全程设计与工程规则

### 5.1 视觉规则

- 风格定位：克制、可信、偏企业软件，而不是营销落地页或炫技型 AI 页面。
- 视觉层级：每个页面只能有一个主任务、一个主要按钮和一个最需要面试官看到的证据区。
- 颜色：语义色必须统一；正文和交互文本满足 WCAG AA 对比度。
- 布局：优先保证 `1440×900`、`768×1024`、`390×844` 三种视口。
- 动效：只用于状态变化和操作反馈，并支持 `prefers-reduced-motion`。
- 资源：登录门户不依赖外部图片；本地离线启动时仍应完整显示。
- 密度：登录门户可以承担产品定位，登录后的业务页面保持紧凑、可扫描，不使用营销式大标题或大量装饰卡片。
- 容器：不在卡片中继续嵌套装饰卡片；只有独立记录、工具面板、重复项目和弹层使用有边框容器。
- 尺寸：导航、图标按钮、状态徽标、闪卡和固定工具栏使用稳定尺寸，加载文字或状态变化不能推动页面跳动。
- 文本：不使用随视口宽度缩放的字号；长文件名、长引用、状态文本和按钮文案必须安全换行或截断并可查看完整内容。
- 图标：继续使用当前原生实现，不为本轮单独引入图标库；图标按钮必须有 `title` 或可访问名称，不能只靠难以识别的符号表达危险操作。

### 5.2 交互规则

- 所有按钮、标签页、表单、折叠区和导航均支持键盘操作和可识别的焦点状态。
- 加载、空状态、错误、成功和不可用状态必须有清楚文案，不能只靠颜色表达。
- Demo、登录、注册三条路径不能互相抢夺主要层级；Demo 是展示入口，登录和注册是账户入口。
- 错误信息只告诉用户可执行的下一步，不暴露堆栈、Key、请求体或敏感配置。
- 保持现有 Cookie 会话和同源请求方式，不在浏览器存储身份令牌或 Provider Key。
- 破坏性操作必须保持明确区分和现有确认流程；不能因为视觉统一把删除、拒绝、取消和普通次要操作做成同一层级。
- 异步操作以最终业务状态为准，测试使用条件等待，不使用固定延迟掩盖竞态。
- 页面切换、目标切换和操作完成后，焦点位置、选中导航和页面标题必须同步。

### 5.3 证据规则

- “已通过”必须有测试输出或人工复核记录。
- 截图必须来自通过门禁的版本，不保留失败版本生成的截图。
- 视觉改变不能破坏原有黄金流程、确认边界、RAG 引用和 FSRS 状态更新。
- 每阶段只形成一个可说明的面试证据，不用代码行数或页面数量替代结果。
- 自动化截图只证明页面在指定夹具下渲染成功；“易理解”“层级清楚”等判断必须另做人工复核。
- Mock、固定离线评测、历史真实 Provider 和浏览器回归继续分别表述，前端优化不得改变既有指标口径。

## 6. 通用阶段门禁

### 6.1 阶段开始条件

每个阶段开始前执行：

```powershell
git branch --show-current
git status --short
git diff --check
```

必须确认：

- 当前分支为 `feature/learning-loop-ux`。
- 工作区中的已有改动都能说明来源；不删除、不覆盖与本阶段无关的用户改动。
- 上一阶段已经提交，或 `FE-00` 中明确标记的初始未提交改动仍在收口范围内。
- Playwright 使用配置自带的 `8019` 测试服务；若端口被其他进程占用，先识别进程，不连接来源不明的已有服务继续测试。
- 页面测试统一使用 Mock Provider 和隔离测试数据库；真实 Key 只用于独立的本地人工演示。

### 6.2 测试与命名规则

- 新增或扩充的阶段测试继续放在 `tests/browser/v7-frontend-refresh.spec.cjs`，测试标题必须包含对应阶段编号，例如 `FE-03`。
- `--grep "FE-XX"` 定向命令必须实际执行至少一个测试；出现 `No tests found` 不能视为通过。
- 修改已有黄金流程测试时，只能更新因 DOM 或可访问名称变化而失效的定位方式，不降低业务断言。
- 优先使用稳定 ID、`data-*`、角色和可访问名称定位，不依赖视觉顺序、完整长文案或脆弱 CSS 层级。
- 每个阶段先跑定向测试，再跑完整 E2E；定向通过不能替代完整回归。

### 6.3 阶段完成定义

一个阶段只有同时满足以下条件才能标记为 `COMPLETED`：

- [ ] 该阶段列出的用户可见结果已经实现，且没有范围外功能变化。
- [ ] 定向 Playwright、前端语法检查、完整 E2E 和 `git diff --check` 通过。
- [ ] 指定视口已人工查看，没有重叠、截断、异常空白、错误状态残留或主要操作被遮挡。
- [ ] 新生成或被覆盖的截图已逐张复核，失败运行产生的截图没有作为证据保留。
- [ ] 浏览器 `pageerror` 和非预期 `console.error` 为 0。
- [ ] 验收记录写明改了什么、为什么、测试结果、截图和已知限制。
- [ ] 本阶段文件已经选择性暂存、复核、提交并推送到指定个人功能分支。

仅仅完成代码修改、单个测试通过或页面“看起来可以”，都不算阶段完成。

禁止使用其他推送目标。若推送失败，只报告失败和本地提交号，不改推送目标、不合并、不强推。

### 6.5 人工视觉复核方法

每个阶段的截图不能只确认“文件已生成”，必须实际打开并逐项检查：

- [ ] 第一眼能看出页面名称、当前任务和主要操作，标题大小与容器密度匹配。
- [ ] 文本、按钮、徽标、图标和输入框没有重叠、截断或意外换行。
- [ ] 页面没有卡片套卡片、装饰性空白过多、单一色相占满全屏或营销页式排版。
- [ ] 桌面侧栏、平板布局和移动底部导航不会遮挡内容或改变页面宽度。
- [ ] 空状态、错误状态、加载状态和完成状态与当前数据一致，没有失败 Toast 或加载残影。
- [ ] 截图中没有真实账号、Cookie、Key、连接串、浏览器扩展、调试面板或公司非公开信息。

Goal 模式执行时应使用本地图片查看工具打开每张证据图；发现问题后修复并由测试重新生成，不手工编辑测试截图。
