## 1. 最终目标

实现一个面向个人学习场景、可恢复、可评测、可解释的完整垂直智能体。

它不是通用 AutoGPT，也不是“LLM + 页面按钮”的工作流包装。最终系统必须能够围绕用户目标自主完成有限步循环：

```text
Objective
-> Observe AgentContext
-> LLM / Rule Decide
-> Decision Guard
-> Select and validate Tool
-> Execute Tool
-> Persist AgentStep
-> Feed Observation into next Decision
-> Human confirmation when required
-> Apply confirmed write
-> Read back changed Context
-> Reflect / stop
```

## 2. 唯一核心演示生命周期

简历和面试只讲一个做深的主场景：

```text
用户创建学习目标并录入资料
-> 启动带 objective 的 AgentRun
-> Agent 发现资料尚未处理
-> 自动生成 chunks、embeddings 和摘要
-> Agent 重新观察到资料状态已变化
-> 根据问题执行语义检索并获得 references
-> 判断资料是否足够并生成回答或补资料建议
-> 根据薄弱点生成复习草稿或任务草稿
-> 高风险写入暂停等待用户确认
-> 用户确认后从原 Run 恢复并写入正式数据
-> AgentContext 读回正式数据变化
-> Agent 判断目标完成并停止
```

任何新增能力都必须直接服务这条生命周期，否则暂不开发。

## 3. 完成定义

第六版只有同时满足以下条件才算完成：

| 维度 | 完成标准 |
|---|---|
| Objective | Run 接收明确目标，Decision 每步都能读取目标 |
| Observe | Context 覆盖目标、任务、资料、检索、问答、测试、复习和反馈状态 |
| Decide | 真实模型能基于 Context、Tool Schema 和历史 Observation 输出严格 JSON Tool Call |
| Guard | 未知工具、非法参数、越权目标和漏确认写入在执行前被拦截或回退 |
| Execute | 至少 6 个真实领域工具，不以页面跳转或纯文字建议冒充执行 |
| Loop | Tool Output 会进入下一次 Decision，模型能根据结果改变动作 |
| Resume | waiting_confirmation 后可从同一个 Run / Step 恢复，不重新开始 |
| Idempotency | 重试和恢复不会重复生成正式任务、闪卡或资料记录 |
| Stop | completed、waiting_confirmation、failed、max_steps 等边界明确，无无限循环 |
| Memory | ActionLog / Run History 会影响后续决策，避免原样重复建议 |
| Observability | 前端能展示 Step、Tool Input/Output、Guard、错误、耗时和停止原因 |
| Evaluation | 有固定场景、量化指标、真实模型记录和失败降级证据 |
| Retrieval | 最终演示使用真实 EmbeddingProvider，Mock embedding 只用于 CI |
| Reliability | 支持工具超时、有限重试、取消、并发 Run 互斥、事务回滚和错误恢复 |
| Reproducibility | 固定依赖、环境变量模板、CI 和一条命令启动，演示可复现 |

## 4. 真实工具清单

最终至少完成以下工具：

```text
1. process_materials
   生成缺失 chunks、embeddings 和摘要，并返回处理结果。

2. search_materials
   根据 query 做语义 Top-K 检索，返回 references、score 和 searchMode。

3. answer_with_sources
   只根据 references 回答；资料不足时返回明确 insufficiency。

4. create_review_draft
   根据资料、问答或弱项生成持久化复习草稿。

5. create_task_draft
   根据 objective 和学习状态生成持久化任务草稿。

6. apply_confirmed_draft
   仅在确认后把草稿写入正式 tasks / flashcards，并保证幂等。
```

可选增强工具必须等以上六项完成后再评估。

## 8. 工程约束

```text
1. 所有正式写入必须经过确认和幂等校验。
2. LLM 只能选择 Registry 中的工具，不能生成任意代码或 SQL。
3. Tool Executor 必须再次校验输入和数据归属，不能只信任 Guard。
4. 每个 Step 必须可追踪，异常不能静默吞掉。
5. 默认测试不得依赖网络、真实 Key 或真实模型。
6. 每个 Batch 必须同时有 pytest、smoke 或评测证据。
7. 不把 rule-based 成功冒充真实模型智能体效果。
8. 最终语义检索评测必须使用真实 embedding；MockEmbeddingProvider 只用于测试。
9. 同一 Run 同一时刻只允许一个 executor 推进，避免并发重复写入。
10. 工具调用必须设置超时；自动重试最多一次，写工具不得无条件重试。
11. 日志和 Step Output 不得记录 API Key、Authorization 或未脱敏敏感数据。
```

## 11. Batch B4 详细需求：持久化草稿

### 11.1 目标

`create_review_draft` 和 `create_task_draft` 必须生成后端可读回的真实草稿，不再只把 drafts 放在 AgentStep 的临时 Tool Output 中。

生成草稿不会修改正式任务或闪卡，因此这一阶段允许自动执行；正式写入统一留给 B5。

### 11.2 数据模型

统一使用 `agent_drafts` 表，避免 review/task 两套状态机重复：

| 字段 | 类型 | 约束与含义 |
|---|---|---|
| id | TEXT | 主键，`agentdraft_*` |
| user_id | TEXT | owner；所有查询和执行必须隔离 |
| goal_id | TEXT | 所属目标，可为空 |
| run_id | TEXT | 来源 AgentRun，必填 |
| step_id | TEXT | 来源 AgentStep，必填 |
| draft_type | TEXT | `review` / `task` |
| payload | TEXT | 规范化 JSON；保存待确认的完整内容 |
| status | TEXT | `proposed` / `confirmed` / `applied` / `rejected` |
| idempotency_key | TEXT | 全局唯一；防止重试重复建草稿 |
| applied_entity_ids | TEXT | 正式写入后的 ID JSON 数组，默认 `[]` |
| created_at | TEXT | 创建时间 |
| updated_at | TEXT | 更新时间 |
| applied_at | TEXT | 正式写入时间，可为空 |

外键策略：

```text
goal_id -> goals.id ON DELETE SET NULL
run_id -> agent_runs.id ON DELETE CASCADE
step_id -> agent_run_steps.id ON DELETE CASCADE
```

幂等键算法：

```text
sha256(user_scope + run_id + step_id + tool_name + canonical_json(payload))
```

同一 Step 重试必须返回原草稿，不能插入第二份。

### 11.3 状态机

```text
proposed -> confirmed -> applied
proposed -> rejected
confirmed -> rejected
applied 为终态，不允许回退
rejected 为终态，不允许 apply
```

B4 只创建 `proposed` 草稿和提供查询；`confirmed/applied/rejected` 的完整行为在 B5 实现。

### 11.4 工具行为

```text
create_review_draft
- draftOnly=true
- requiresConfirmation=false
- 根据 materialIds / weakAttemptCount 生成 payload
- payload 至少包含 materialId、front、back、sourceReason

create_task_draft
- draftOnly=true
- requiresConfirmation=false
- 根据 goalIds / taskIds / objective 生成 payload
- payload 至少包含 goalId、title、detail、date、priority、sourceReason
```

工具输出统一返回：

```json
{
  "observation": "Persisted 1 task draft.",
  "data": {
    "drafts": [],
    "createdCount": 1,
    "reusedCount": 0
  },
  "terminal": false
}
```

### 11.5 API

```text
GET /api/agent/drafts?goalId=&draftType=&status=&limit=
GET /api/agent/drafts/{draft_id}
```

API 必须执行 userId/goalId 隔离；列表默认按 `created_at DESC`。

## 12. Batch B5 详细需求：确认与幂等正式写入

### 12.1 目标流程

```text
Agent 自动生成 proposed 草稿
-> Decision 提出 apply_confirmed_draft(draftIds)
-> Runtime 创建 ActionLog 并进入 waiting_confirmation
-> 前端展示草稿完整内容
-> 用户 accepted / rejected
-> accepted 时 ActionLog 与关联 drafts 在同一事务更新为 accepted / confirmed
-> rejected 时 ActionLog 与关联 drafts 在同一事务更新为 rejected
-> accepted 后原 Run 恢复
-> Executor 在事务内校验草稿并写入正式表
-> draft=applied，保存 appliedEntityIds
-> ActionLog=applied
-> 下一轮 Context 读回正式变化
```

只允许一次有意义的确认：生成草稿不确认，正式写入时确认。

ActionLog 的 `proposedPayload` 必须包含 `draftIds`。PATCH ActionLog 状态时，后端根据这些 ID 同步推进草稿状态；如果任一草稿不属于当前用户、状态不允许转换或更新失败，ActionLog 与 drafts 都必须回滚。

### 12.2 apply_confirmed_draft 契约

```text
riskLevel=high
requiresConfirmation=true
draftOnly=false
inputSchema={draftIds: list[str] required}
```

执行前必须验证：

```text
1. 所有 draft 属于当前 user / goal。
2. 所有 draft 状态为 confirmed。
3. review payload 能映射到 flashcards；task payload 能映射到 tasks。
4. 同一批次不得混入 rejected 草稿。
5. applied 草稿重试时直接返回原 appliedEntityIds。
```

### 12.3 事务与幂等

```text
SQLite 正式写入、draft 状态更新和 appliedEntityIds 保存必须在同一事务完成。
任一步失败全部回滚。
重复 execute / resume 不得产生重复 tasks 或 flashcards。
写工具发生超时后不得盲目重试，必须先按 idempotencyKey 查询结果。
```

### 12.4 B5 验收

```text
[x] B5-01 未确认草稿绝不能写正式表。
[x] B5-02 accepted 后可从原 Run/Step 恢复并写入。
[x] B5-03 rejected 后 Run 能继续或安全停止，不执行写入。
[x] B5-04 重复 resume / execute 正式记录只生成一次。
[x] B5-05 写入异常时正式表和 draft 状态全部回滚。
[x] B5-06 用户/目标越权草稿被 Guard 或 Executor 拦截。
[x] B5-07 基础链路已证明：有剩余 step budget 时，写入后 Context readback 能改变下一轮 Decision。
```

B5-07 只验收正常剩余步数下的基础闭环，不代表 B6 已完成。B6 还必须保证确认步骤耗尽 step budget 时，正式写入后的 Context / Decision 仍会被强制重建并持久化。

## 13. Batch B6 详细需求：正式写入后的强制 Readback

### 13.1 目标与执行顺序

`apply_confirmed_draft` 成功后，Runtime 必须先完成正式写入后的 Context / Decision readback，再判断是否继续循环或进入终态。readback 不依赖剩余 step budget。

```text
accepted ActionLog + confirmed drafts
-> apply_confirmed_draft 事务提交
-> waiting Step 更新为 completed
-> 重新读取完整 Step History
-> 按原 Run 的 userId / goalId / objective / decisionMode 构建 Context
-> 基于该 Context 生成下一轮 Decision
-> 持久化 Run.contextSnapshot / decisionSnapshot
-> 有预算则继续；无预算则带最新快照进入 max_steps
```

### 13.2 字段与快照语义

B6 不新增数据库字段，不执行 schema migration，复用现有持久化字段和 Context 输出：

```text
AgentStep.contextSnapshot
  始终表示该 Step 工具执行前的 Context，不在执行后原地覆盖。

AgentRun.contextSnapshot / decisionSnapshot
  始终表示最近一次成功工具执行后的最新观察和下一轮决策。

AgentRun.currentStep
  只统计持久化 AgentStep；readback 本身不增加 currentStep。

Context 变化证据
  summary.taskTotal
  summary.flashcardTotal
  summary.draftProposedCount
  drafts.proposedCount / confirmedCount / appliedCount / rejectedCount
  tasks[].nextOpen / review.new / review.materialsNeedingReview

正式实体关联证据
  agent_drafts.appliedEntityIds
```

readback 不新增 AgentStep、不消耗 step budget，也不改变已完成 Step 的 `stepIndex`。正式任务应能通过 `tasks[].nextOpen[].id` 与 `appliedEntityIds` 对应；正式闪卡应通过 flashcard / review 计数和所属资料状态证明已进入 Context。

### 13.3 状态机与停止规则

```text
ActionLog: proposed -> accepted -> applied
Draft:     proposed -> confirmed -> applied
Step:      waiting_confirmation -> completed
Run:       waiting_confirmation -> running -> completed | max_steps | failed
```

约束：

```text
1. apply 事务成功后必须先把 waiting Step 更新为 completed，再读取 Step History。
2. 新 Decision 必须读取包含 apply Tool Output 的完整 Step History。
3. 有剩余预算时直接使用本次 readback 产生的 Decision 继续循环，不能重复调用模型生成同一轮 Decision。
4. 无剩余预算时，先持久化新 Context / Decision，再设置 status=max_steps、stopReason=max_steps。
5. readback 后的 Decision 不能再次请求同一批已 applied Draft。
6. 重复 execute / resume 仍通过 appliedEntityIds 和既有幂等规则返回原正式记录。
```

### 13.4 API 契约

B6 不新增公共 API，不改变现有请求或响应字段：

```text
PATCH /api/agent/action-logs/{log_id}
  负责 accepted / rejected，并同步 confirmed / rejected Draft 状态。

POST /api/agent/runs/{run_id}/execute
  负责从原 Run 恢复、执行 apply、完成强制 readback，并返回最新 Run 详情。

GET /api/agent/runs/{run_id}
  必须返回已持久化的最新 contextSnapshot / decisionSnapshot / steps。

GET /api/agent/context
  继续提供独立的当前状态读取，用于核对 Run snapshot 与实时 Context。

GET /api/agent/runs
  仍只返回 contextSummary / decisionSummary，不新增完整 snapshot。
```

所有 readback 必须复用原 Run 的 `userId` 和 `goalId`，不得扩大到全局或其他用户/目标数据。

### 13.5 失败与兼容处理

```text
Context 构建失败：
  Run.status=failed
  Run.stopReason=context_readback_error
  Run.error 保存脱敏后的明确错误

Decision 生成发生未被 Provider fallback 吸收的异常：
  Run.status=failed
  Run.stopReason=decision_readback_error
  Run.error 保存脱敏后的明确错误
```

readback 发生在正式写入事务提交之后，因此 readback 失败不得回滚已经 applied 的正式记录、Draft 或 ActionLog。后续恢复必须先按既有幂等键和 `appliedEntityIds` 查询结果，不能重复写入。B6 不新增 Run status，只使用已有 `failed` / `max_steps`；新的 stopReason 使用现有 TEXT 字段。

## 14. Batch C 详细需求：真实模型与记忆

### 14.1 真实 EmbeddingProvider

最终演示和 D3 检索评测必须使用真实 embedding 模型。配置建议：

```text

```

真实 Provider 失败时可回退关键词检索，但评测报告必须标明实际 provider，不能把 Mock 结果当成真实语义效果。

### 14.2 Decision JSON 契约

```json
{
  "stateSummary": "string",
  "problems": [],
  "nextAction": "registered_action_type",
  "reason": "string",
  "requiresConfirmation": false,
  "proposedActions": [
    {
      "type": "registered_action_type",
      "payload": {},
      "requiresConfirmation": false
    }
  ],
  "reflection": "string"
}
```

Guard 校验顺序：JSON object -> 必填字段 -> 已注册 action -> payload schema -> owner scope -> risk/confirmation。

### 14.3 失败策略

```text
JSON/Schema 错误：最多一次格式修复；仍失败则回退 rule-based。
超时/网络错误：记录 fallbackReason，不自动重复写工具。
重复 action + payload：Run 内按 fingerprint 跳过并触发 no_progress/reflection。
上下文过长：保留 objective、最近 Step、关键状态和摘要，记录裁剪信息。
未知工具或越权参数：Guard fallback，Executor 再次拒绝。
```

### 14.4 Memory 与 Reflection

```text
短期记忆：当前 Run 最近 8 个 AgentStep。
长期记忆：ActionLog / Feedback Memory 中 accepted、rejected、deferred、applied。
Reflection：只在 completed、failed、max_steps、no_progress 时生成运行总结；不得修改工具和系统规则。
```

至少验证：拒绝后换策略、已 applied 不重复、no_progress 能停止、失败反思包含工具错误。

### 14.5 真实模型验收

至少保留 5 类真实模型记录：正常三步循环、资料不足、非法参数 Guard、确认恢复、模型/工具失败降级。

每次记录 model、provider、promptVersion、耗时、stepCount、toolSequence、terminalStatus 和 fallbackReason；不记录 Key。
