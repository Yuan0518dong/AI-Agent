# 每日工作安排规则

用途：每天开始安排工作时，用最少上下文判断项目状态、生成当天任务，并留下明天可衔接的入口。

## 1. 低 token 原则

每天不要全量重读所有文档。

默认只读：

```text
1. git status --short --branch
2. git log --oneline --decorate -n 5
3. docs/status/当前状态.md
```

只有出现以下情况，才扩展读取更多文档：

```text
1. 项目阶段发生变化，例如 dev 准备合 main。
2. 当前状态.md 信息不足。
3. 当前状态.md 和代码状态不一致。
4. 当天要改 API、数据对象或模块边界。
5. 用户明确要求重新审查 PRD、技术方案或分工。
```

扩展读取顺序：

```text
1. docs/daily/最新一份工作安排.md
2. docs/status/项目进度记录.md
3. 与当天任务直接相关的代码或 API 文档
```

## 2. 每天只维护一份日文档

每日文件统一放在：

```text
docs/daily/YYYY-MM-DD工作安排.md
```

不再拆成“工作分工”和“执行清单”两份，避免重复。

每日工作安排里同时包含：

```text
1. 当前判断
2. 今日总目标
3. 陈今日任务
4. 赵今日任务
5. 共同任务
6. 今日不做
7. 验收标准
8. 明日入口
```

## 3. 每日判断顺序

每天先回答四个问题：

```text
1. 当前在哪个分支，工作区是否干净？
2. 昨天留下的明日入口是什么？
3. 今天主线卡在哪里？
4. 今天只保哪一个主目标？
```

项目主线固定为：

```text
目标 -> 资料 -> AI 整理 -> 计划 -> 打卡 -> 进度
```

当天任务如果不服务这条主线，默认不进硬目标，除非它是 P0/P1、合 main 必需项或导师明确要求。

## 4. 分工默认规则

```text
陈：目标管理 -> 行动计划 -> 今日任务 -> 打卡 -> 进度统计 -> 后端骨架
赵：资料管理 -> AI 整理 -> 闪卡 / 测试题 -> 成长问答
共同：MVP 边界、接口字段、集成联调、演示验收、是否合 main
```

每天每人最多安排：

```text
1 个主任务 + 2 个小任务
```

P0/P1 优先于新功能。

## 5. 输出格式

每天安排工作时，用这个短格式：

```text
当前判断：
今日总目标：
陈今日任务：
赵今日任务：
共同任务：
今日不做：
验收标准：
明日入口：
```

如果需要问题清单，单独追加：

```text
编号：
负责人：
优先级：P0 / P1 / P2 / 待确认
复现：
结论：
下一步：
```

## 6. 分支规则

```text
feature/* -> dev -> main
```

规则：

```text
1. 个人模块开发在 feature 分支。
2. 联调和验收在 dev。
3. main 只放稳定可演示版本。
4. dev 没有 P0 且完整主线可演示后，才考虑合 main。
```

## 7. 每日结束必须更新当前状态

每天结束先更新：

```text
docs/status/当前状态.md
```

至少更新这些字段：

```text
更新时间
当前阶段
今日主目标
今日第一步
已验证
未解决问题
最新日文档
```

其中“今日第一步”必须是明天可直接执行的具体动作，例如：

```text
先跑 python backend/smoke_api.py
先修 /api/tasks/today 今日任务为空的问题
先从 app.js 目标创建流程接 POST /api/goals
先实现 POST /api/materials
```
