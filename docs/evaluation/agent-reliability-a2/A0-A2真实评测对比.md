# A0–A2 真实 Agent 评测对比

评测日期：2026-07-20

## 结论

A2 的动作契约对齐与状态感知 allowed-action policy 对真实 DeepSeek 决策产生了正向效果：工具选择率由 `0.6333` 提升到 `0.75`，确认完整性由 `0.5556` 提升到 `0.6667`，失败 Run 由 22 降至 15，p50 延迟、请求数、Token 和估算成本同时下降。

但是 A2 没有达到预设的工具选择 `>=0.80` 和确认完整性 `>=0.85`，因此当前 Draft PR 不应合并到 `main`，也不能在简历中把 A2 描述成“真实 Agent 已稳定”。

## 可比性

- A0 与 A2 使用相同 `backend/evaluation/agent_scenarios.json`。
- 两次均为 20 场景 × 3 次，即 60 Run。
- A0 Prompt/Runtime 为第七版基线；A2 Prompt version 为 `agent-reliability-a2-policy-v1`。
- A2 仍关闭格式修复重试，单请求仍限制 12,000 UTF-8 bytes 和 350 completion tokens。
- A0 原始 JSON 的 SHA-256 在 A2 前后保持 `DFA51A1F2BE2C20381EADC795FDAD38FE2B5E1887653578DD22A8225D3AC569B`，没有被覆盖。

## 剩余失败

A2 的 15 个失败 Run 分布在 7 个场景，其中只有 `014` 和 `016` 仍为 3/3 系统性失败；A0 中这一数字为 7 个场景。剩余失败族：

```text
semantic_routing: 4
confirmation_state: 3
tool_failure_recovery: 3
scope_and_evidence: 2
feedback_memory: 2
terminal_control: 1
```

`014` 表明“恢复并应用已确认复盘草稿”仍不能只依赖模型从目标文字推断阶段；下一步应让 Runtime 确定性控制确认和恢复状态。`016` 的固定 fixture 没有预置 draft，却要求工具序列包含 `apply_confirmed_draft`，适合作为 Guard/事务故障注入测试，但与正常产品状态不完全一致；后续若修正 fixture，必须建立新版本并同时保留旧结果。

## fallback 指标限制

A2 原始报告记录 `fallbackDecisionCount=27`，但当前 runner 只累计持久化 Step 中的 decision snapshot。A2 有 12 个失败 Run 在执行任何 Step 前安全结束，其终态 decision 没有进入逐 Step 统计，因此 `27` 只能视为“已记录的 Step 级 fallback 下限”，不能与 A0 的 `84` 做精确降幅宣传。

评测后已修复 runner：后续报告会在终态 decision 与 Step decision 不重复时把它纳入 fallback 计数。本次 A2 不伪造或回填无法从聚合报告证明的精确值。

## A3 建议

1. 确认、拒绝、恢复和已存在 draft 的阶段迁移由 Runtime 确定性控制，模型只填充语义参数。
2. 对明确的“创建复盘草稿”目标，在完成 draft 前不开放 `answer_only`。
3. 将模型输出从完整 Decision 缩减为 action type、payload 和简短 reason，其余状态字段由服务端补齐，降低触及 350 completion token 上限的概率。
4. 为 `016` 新增带无效 draft 的 v2 fixture，同时继续报告旧 fixture 结果。
5. A3 仍使用固定 A0 集做向后对比；如果增加 v2 fixture，应单独报告，不混入原成功率分母。
