# 两人协作开发分工文档

## 1. 文档目的

本文件用于明确通用成长学习助手 App 在两人开发阶段的职责边界、协作流程、Git 使用方式和功能验收标准。

目标是避免口头沟通后遗忘、需求反复变化、代码互相覆盖、功能完成标准不清楚等问题。

## 2. 协作角色

两人开发阶段建议采用“产品与体验负责人 + 技术与实现负责人”的方式分工。

这种方式比简单地分成“一个前端、一个后端”更适合早期项目，因为早期最重要的是先确认产品方向和核心闭环。

## 3. 角色一：产品与体验负责人

建议由你主要负责。

主要职责：

1. 明确产品定位和目标用户。
2. 维护 PRD 产品需求文档。
3. 确定第一版功能范围。
4. 梳理页面结构和用户流程。
5. 决定功能优先级。
6. 收集和整理用户反馈。
7. 测试功能是否符合预期。
8. 判断功能是否可以验收。
9. 维护需求变更记录。
10. 协调每周开发计划。

需要重点关注的问题：

- 这个功能是不是第一版必须做？
- 用户能不能看懂这个页面？
- 目标、资料、计划、打卡这条流程是否顺畅？
- 功能做完后是否真的解决用户问题？

## 4. 角色二：技术与实现负责人

建议由同事主要负责。

主要职责：

1. 选择前端、后端、数据库和部署方案。
2. 搭建正式项目结构。
3. 维护 Git 分支和代码合并。
4. 实现核心功能。
5. 接入真实大模型 API。
6. 设计数据库表和接口。
7. 实现资料解析、计划生成、闪卡、打卡等功能。
8. 处理部署、环境变量和接口安全。
9. 修复测试中发现的问题。
10. 保证代码质量和基本可维护性。

需要重点关注的问题：

- 代码是否方便后续扩展？
- 用户数据是否会丢失或串数据？
- AI 接口是否有成本和失败处理？
- 功能是否可以稳定运行？

## 5. 推荐分工表

| 工作内容 | 产品与体验负责人 | 技术与实现负责人 |
|---|---|---|
| 产品定位 | 主负责 | 参与讨论 |
| 目标用户 | 主负责 | 参与讨论 |
| PRD 文档 | 主负责 | 技术评估 |
| 页面流程 | 主负责 | 参与评审 |
| UI 原型 | 主负责/共同 | 共同 |
| 技术架构 | 参与理解 | 主负责 |
| 数据库设计 | 提需求 | 主负责 |
| 接口设计 | 提使用场景 | 主负责 |
| 前端开发 | 可辅助 | 主负责 |
| 后端开发 | 了解逻辑 | 主负责 |

| 功能测试 | 主负责 | 修复问题 |

## 6. 第一阶段开发目标

第一阶段目标不是做一个完整大而全的 App，而是做出一个可以演示的最小可用版本。

最小可用版本需要完成：

1. 创建成长目标。
2. 添加学习或成长资料。
3. AI 整理资料重点。
4. 根据目标生成行动计划。
5. 生成闪卡或测试题。
6. 每日任务打卡。
7. 查看目标进度。

## 7. Git 分支规则

建议使用以下分支结构：

```text
main                 稳定版本
dev                  日常开发版本
feature/目标名称      具体功能分支
```

示例：

```text
feature/goal-management
feature/material-management
feature/ai-summary
feature/study-plan
feature/check-in
feature/progress-dashboard
```

基本流程：

1. 从 dev 新建功能分支。
2. 在功能分支完成开发。
3. 自测通过后合并回 dev。
4. dev 测试稳定后合并到 main。
5. main 上的重要版本打 tag。

## 8. Commit 提交规范

建议每次提交只做一类事情，提交信息尽量清楚。

推荐格式：

```text
feat: 添加目标管理功能
fix: 修复资料删除后闪卡未同步删除的问题
docs: 更新通用版 PRD
style: 调整首页布局
refactor: 整理计划生成逻辑
test: 增加目标创建测试
```

常用类型：

- feat：新增功能
- fix：修复问题
- docs：文档修改
- style：样式调整
- refactor：代码重构
- test：测试相关
- chore：项目配置或杂项

## 9. 每周协作节奏

建议每周至少同步一次，每次控制在 30 分钟以内。

固定讨论 4 个问题：

1. 这周完成了什么？
2. 当前卡在哪里？
3. 下周要做什么？
4. 需求或优先级有没有变化？

同步结束后，要把结论写进任务清单或文档，不只停留在口头沟通。

## 10. 功能验收方式

每个功能完成后，至少按以下标准验收：

1. 用户能不能正常完成这个操作？
2. 页面提示是否清楚？
3. 数据刷新后是否还在？
4. 删除、修改等危险操作是否有确认？
5. 出错时用户是否知道发生了什么？
6. 是否影响其他已有功能？

示例：创建目标功能验收标准：

- 可以输入目标名称、方向、当前水平、截止时间和每天投入时间。
- 创建成功后目标出现在目标列表。
- 系统可以基于目标生成行动计划。
- 刷新页面后目标仍然存在。
- 删除目标前需要用户确认。

## 11. 需求变更规则

早期项目一定会变，但不能每天随意改方向。

建议规则：

1. 小文案、小样式可以直接调整。
2. 新增功能必须先写进 PRD 或任务清单。
3. 会影响开发周期的需求，需要两个人确认。
4. 已经开发中的功能，除非问题明显，否则不要频繁改目标。
5. 每次版本发布前冻结需求，只修问题。

## 12. 推荐近期任务拆分

近期可以按以下顺序推进：

1. 更新产品定位为通用成长学习助手。
2. 整理页面原型和文案。
3. 确认第一版技术栈。
4. 设计正式数据库表。
5. 搭建前后端项目。
6. 实现目标管理。
7. 实现资料管理。
8. 接入 AI 总结。
9. 实现计划生成和打卡。
10. 做一次完整演示版本。

## 13. 当前建议

两个人协作时，最重要的不是一开始做很多功能，而是保持边界清楚、节奏稳定、版本可回退。

建议你主要盯住“用户到底要什么”和“功能是否好用”，同事主要负责“如何稳定实现”。这样两个人的优势不会互相打架，项目也更容易持续推进。
